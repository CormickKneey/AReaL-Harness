# D5（P1）：设计规则来源收敛与文档减重

## 1. 背景与当前问题

- 设计相关的文档分布在至少五个位置：
  - `design/`：46 篇，约 186 KB，跨产品的原则、组件、模式、内容、决策和归档
  - `clients/gui/design-system/`：27 篇，约 285 KB，GUI 合同、Base、交互分类、流程和练习
  - `packages/ui/README.md` 和 `agent-guide.md`
  - 组件目录里就近的 `*.md` 合同
  - `registry.json`、`surfaces/*.json` 等结构化数据
- 最大的几篇单篇就有 24–34 KB：`patterns.md`、`worktrees.md`、`conversation-flow.md`、`exercises/conversation-flow.md`。
- [设计系统 README](../design-system/README.md) 自称每类问题都有"唯一规则位置"，但实际要写一个普通页面，需要按开工顺序读交互分类、页面组合、生产目录、基础规则、控件合同、结构化流程和完成条件，至少跳 6–7 篇文档。
- 后果：Agent 和新人都很难判断应该以哪份为准；上下文预算被文档占满；规则之间容易悄悄出现矛盾；而这些文档管理的界面只占约 30%（见 [D2](D2-design-system-adoption.md)）。

## 2. 目标与非目标

目标：

- 只有两个入口：使用者入口（写页面、选组件、写样式）和维护者入口（改系统、准入、治理）。
- 每条规则有 ID，并且只在一个位置定义；其他位置只能引用 ID。
- 活跃文档总量明显下降，规则不能丢失。

非目标：不改变任何规则的内容（只做搬迁、合并、归档和编号）；不删除历史证据（移到归档）。

## 3. 架构决策

| 决策 | 状态 | 内容 |
| --- | --- | --- |
| D1：两个入口 | 已定 | 使用者入口：`packages/ui/README.md`（合并 `agent-guide.md` 的要点）+ 生成的 Token 速查 + 组件合同。维护者入口：`clients/gui/design-system/README.md` |
| D2：`design/` 的定位 | 已定 | 只保留跨产品（GUI、Web、Remote）的原则、术语和决策记录；GUI 专属内容搬进 `clients/gui/design-system/`；过程性材料（练习、审查记录、拆解分析）搬进 `design/archive/` |
| D3：规则编号 | 已定 | 在 `registry.json` 中登记规则：`{id, title, owner(文件#锚点), strength(必须/默认/可探索)}`，例如 `R-COLOR-001`。正文中定义规则时带上 ID；其他文档只写 ID 和链接，不复述内容 |
| D4：使用者路径的上限 | 已定 | 完成一个普通页面任务（例如新增一个设置分组），使用者最多读 2 篇文档加对应组件合同 |
| D5：仓库入口链接 | 已定 | `AGENTS.md` 的"GUI 设计入口"段落链接到 `design-system/README.md#开工顺序` 和 `governance.md#完成条件`；搬迁时必须保留这些锚点，或同步修改 `AGENTS.md` |

## 4. 确定性路径

1. 盘点：列出全部设计文档，给每篇标注"使用者 / 维护者 / 跨产品原则 / 过程证据"四类之一，写进 PR 正文。
2. 规则编号：从各文档中提取规范性语句（含"必须""不得""默认"等措辞的条目），在 `registry.json` 中登记 ID 和归属位置。
3. 搬迁和合并：按 D1、D2 重排；重复描述改为引用 ID。
4. 写校验脚本（并入 `verify:design`）：
   - 每个规则 ID 只在一个位置定义；
   - 被引用的规则 ID 都存在；
   - 使用者入口文档的总字数不超过上限（例如 12 KB，具体值在盘点后确定）。
5. 运行 `python3 scripts/check-docs.py`，修复所有链接；检查 `AGENTS.md` 和 PR 模板中的锚点。

## 5. 不确定性路径

核心问题：收敛后 Agent 真的会做得更好吗？这无法靠静态检查回答。

- 假设 H1：入口收敛后，Agent 完成同一个 GUI 小任务时读取的文档更少，违反设计规则的次数不会增加。
- 实验设计：
  - 准备 3 个固定的小任务（新增设置项、新增一个带审批的卡片、修改一个列表的空状态），每个任务写清验收条件。
  - 收敛前后，各让编码 Agent 在全新上下文中执行，每个任务重复 3 次；记录读取的文档数量、上下文中设计文档占用的 token、`verify:design` 和 `test:design` 的结果，以及人工评审发现的违反规则次数。
  - 这些任务属于开发集，只用来比较文档结构，不代表 Agent 整体能力（遵循 [Agent 改进方法](../../../docs/development/agent-improvement.md) 中关于开发集的约束）。
- 证伪条件：收敛后违反规则的次数明显增加，说明删掉或移走的内容里有 Agent 实际需要的信息；需要找出缺失的规则，并补回使用者入口。

## 6. 实施切片

1. PR-1：盘点和规则编号（只改数据和文档标注，不搬迁）。
2. PR-2：收敛前的 Agent 基线实验记录。
3. PR-3：`design/` 和 `design-system/` 的搬迁、合并与归档。
4. PR-4：校验脚本。
5. PR-5：收敛后的 Agent 对照实验记录。

## 7. 验收标准

确定性：

- [ ] 每个规则 ID 唯一定义、引用都能解析（校验脚本通过）。
- [ ] 活跃设计文档（不含 `archive/`）的总量相比当前（约 470 KB）下降至少 40%。
- [ ] 使用者入口满足字数上限。
- [ ] `check-docs.py` 通过；`AGENTS.md` 和 PR 模板中的链接全部有效。

不确定性：

- [ ] 收敛前后的对照实验记录（3 个任务 × 3 次 × 2 组），包括不利结果；结论由人判断。

## 8. 防复发约束

| 层 | 条目 |
| --- | --- |
| L1 规则 | `AGENTS.md`：设计规则只能在登记的归属位置定义；其他文档引用规则 ID，不复述内容 |
| L2 Skill | `.agents/skills/gui-change/SKILL.md` 只链接使用者入口，不再链接维护者文档；`.agents/skills/design-system-maintain/SKILL.md` 负责维护者流程（新规则登记、准入、归档） |
| L3 Lint | 无（文档不经过 lint） |
| L4 CI | 规则 ID 校验、使用者入口字数上限并入 `verify:design`；`check-docs.py` 必跑 |
| L5 棘轮 | `activeDesignDocBytes`（down）、`userEntryDocBytes`（不超过上限） |

## 9. 风险与回滚

- 搬迁打断外部链接或 Agent 的既有习惯：保留旧路径的跳转说明一个周期，并在 PR 正文列出所有路径变化。
- 合并时规则被悄悄改写：PR-3 规定只能搬迁和引用，不能改写措辞；评审时按规则 ID 逐条核对。
