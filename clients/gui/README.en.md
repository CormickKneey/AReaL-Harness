# AReaL Harness GUI

The complete desktop client contains a React renderer, Electron native adapter, and public dependencies. It is a peer of CLI/TUI/Web in the Clients layer. Core owns sessions, history, model loops, and scheduled tasks; Runtime executes tools. Mobile source migration is deferred; desktop pairing remains available.

Web/PWA Remote v2 boundaries are documented in the [architecture](../../docs/design/remote-control.en.md), [API](../../docs/api/remote-control.en.md), [connectivity guide](../../docs/guides/remote-control.en.md), and [acceptance plan](../../docs/development/remote-control-testing.en.md). RC-01/RC-02/RC-03 provide a default-disabled loopback read-only entry, browser requests with desktop confirmation, explicit project scope and device revocation. Effective capabilities include Host/project observation and a bounded Core work/attention overview, including sessions never opened in the GUI; detail and write methods are not yet advertised. Relay, real phones and public deployment require later implementation and acceptance.

Update recovery and menu stop share lifecycle observation and stopping. Normal stop still protects paused Queues containing pending input. Explicit cancellation preserves input and schedules and carries the cancel intent through the final public service host. A changed project scope or Core generation requires new confirmation; partial exits and unknown outcomes do not appear as normal operation. `pnpm --dir clients/gui run test:lifecycle` checks Queue retention and safe exit against real Core, plus menu cancellation, attachment to the original service with a different requested config path, and update recovery in isolated Electron. Ordinary reopen shows no recovery dialog. Explicit stop confirmations use fixture responses; no update is downloaded or installed.

Legacy adapters without lifecycle version 2 retain observation; no cross-layer cancellation fallback is attempted. A known legacy Desktop partial-stop record exposes inspection and an explicit recovery action in the backend banner and settings. Inspection checks original Host identities, admission and resource settlement. Exited targets additionally require a clean Host shutdown marker and released instance/Store locks; a missing PID or socket is insufficient. Unknown, draining, busy or replaced targets retain their records and show the blocker. After confirmation, a new safe stop targets only the original generations verified as idle. A lost recovery-stop response is inspected without resubmission. The current backend starts only after all original Hosts confirm cleanup and the old Desktop exits. An unresponsive Desktop manager requires a separate confirmation before ending that manager; Core/Runtime receive no process signals. Configuration, workspaces, history and tool UNKNOWN records remain intact; the original stop record is archived, and interrupted recovery can be checked again. `pnpm --dir clients/gui run test:legacy-recovery` uses an isolated historical Desktop, current GUI/Core and a local model; `AREAL_RECOVERY_SCENARIO=exited` covers a completed Host stop whose response was unknown.

## Development

Run from the repository root with Node.js 22.19+, pnpm 11.7.0 and the repository Rust toolchain. Use the same Node.js 22 LTS version as CI for both packaging and validation:

```sh
make build
make gui-install
make gui
```

`make gui-build` runs `pnpm install --frozen-lockfile` before building the renderer. `make gui` and `make gui-package` share this step, automatically synchronizing dependencies and installation records after branch or version changes. A lockfile mismatch stops the command without updating the lockfile. `pnpm --dir clients/gui typecheck` checks renderer and shared desktop contract JSDoc types (not all Electron CJS implementations); `pnpm --dir clients/gui run verify` checks the public source boundary. This module has its own pnpm lockfile; existing SDKs retain npm. Dependencies use the public npm registry; initial Electron/Core tool installation needs network access.

After installing locked dependencies, `make gui-install` explicitly runs the official Electron installer to download the pinned native runtime.

`AREAL_CORE_BIN` selects an absolute trusted Core path; development defaults to `target/debug/areal`. Development data is isolated under `AReaL Harness GUI Dev/<checkout digest>`; installed builds use `AReaL Harness GUI`. Existing desktop installations and data are not imported or replaced. `AREAL_GUI_USER_DATA`, `AREAL_CORE_HOME`, and `AREAL_HARNESS_SERVICE_HOME` explicitly select isolated directories. Model configuration defaults to the CLI's `~/.areal/config.toml`; Core owns parsing, validation, and saving. `AREAL_HARNESS_HOME` changes the Core configuration home, and `AREAL_CORE_CONFIG` explicitly selects another file. Reads do not create configuration; Core creates the default file on first save. Configuration in old GUI isolated directories is not merged automatically.

Explicitly select `AREAL_CORE_SANDBOX_PROFILE=native` before starting the GUI, or `--sandbox-profile native` for `areal service ensure/restart`, to request the native Runtime sandbox. The default remains `full-access`. The profile participates in deployment compatibility; stop active work and explicitly restart when changing it. Side chat offers read-only access to current workspace files only when Core verifies the native isolation capability. If native isolation is unavailable, startup fails closed; there is no fallback to full access.

The configuration file is selected in this order: `AREAL_CORE_CONFIG`, `AREAL_HARNESS_CONFIG`, then `config.toml` under the Core configuration home. That home uses `AREAL_HARNESS_HOME` first; otherwise it uses `.areal` under `AREAL_CORE_USER_HOME`, or the current user's home when that override is absent. Relative explicit paths resolve against the GUI launch directory. Both the effective configuration path and configuration home participate in a new service's deployment identity. Ordinary reopen compares the requested deployment with the running service. Matching deployments are reused silently. Changed configuration paths or homes retain the running service and expose an explicit update action. The first save of a previously missing default file preserves its identity. Projects within one GUI adapter share this configuration; switching projects does not select another upload configuration.

Both development and installed macOS builds require a working `/usr/bin/python3` to launch Runtime and trusted tool helpers; install Xcode Command Line Tools with `xcode-select --install`. The interpreter is not bundled. Shared-service startup checks availability and returns an actionable error.

The macOS GUI backend reads static system HTTP, HTTPS and SOCKS proxies for Core, model connection tests and subscription requests; explicit environment variables take precedence. Bypass rules, restart requirements and limitations are documented in [proxy configuration](../../docs/guides/configuration.en.md#proxies). `pnpm --dir clients/gui run test:proxy` verifies actual HTTP forwarding, HTTPS CONNECT, SOCKS5 remote DNS, backend TCP relays and direct local connections. Set `AREAL_TEST_MODEL_PROXY_BIN` to the compiled `core/engine/tests/model_proxy.rs` test executable to also verify real Core HTTP/HTTPS streaming responses.

Application code retains development debugging behavior, and the release profile is unchanged.

`AREAL_CORE_BIN=/absolute/path/to/areal pnpm --dir clients/gui run test:startup` runs isolated real Electron, Core, and Runtime processes. It defaults to five process-cold restarts with retained synthetic history and checks model availability, history restoration, duplicate-submission prevention, and shutdown cleanup. Set `AREAL_STARTUP_BASELINE_BIN` to alternate between two independent builds. `AREAL_STARTUP_ROUNDS` controls the number of rounds. The script retains per-round logs, screenshots, and a manifest. It does not clear system caches or use real providers or user credentials.

The renderer accesses the adapter through narrow preload IPC. Application Quit stops its complete owned engine set; window close retains the application session. Main owns the Desktop lifetime writer, and Desktop owns each GUI Host writer. EOF after owner loss triggers existing bounded supervision cleanup. Explicit stop, update, and quit retain original generation checks, durable request IDs, partial results, and UNKNOWN recovery. Historical UNKNOWN remains inspectable and does not become successful execution. Backends lacking lifecycle capabilities remain available for inspection and explicit migration.

Window reopen and connection recovery reuse only the same application owner. A new application that finds a detached legacy backend or another app run permits observation and explicit safe migration without silently adopting, cancelling, or replacing it. The trusted adapter uses the selected installation’s absolute CLI path. `ensure --no-auto-restart` checks ownership, and explicit lifecycle operations bind the original Desktop, Core generations, and request IDs. The owned registry includes hidden and disconnected projects plus accepted startup work. Completed targets are not stopped twice, unknown acceptance reads the original request, and restored workspaces use authoritative snapshots without replay.

The resident Desktop service declares the current command contract through `service.commandContract`. An older service without this declaration continues to expose running work, history, and compatible queue management; lifecycle writes additionally require version 2 capabilities. Main rejects newer message submission, feedback, plugin Apps/forms, the new default-model operation, and trajectory toggling before dispatch. Input and feedback drafts remain intact. The UI offers an Update backend action, which reconnects only after confirmed shutdown. It does not probe with writes or automatically replay requests. Core capabilities do not establish Desktop forwarding semantics.

`AREAL_CORE_BIN=/absolute/path/to/private/.local/dev-bin/<slot>/areal pnpm --dir clients/gui run test:service-reopen` checks two window close/reopen cycles with the same owner, Desktop, Core generation, active Turn, and model stream. Application exit then stops those engines. Relaunch creates a new owner and generation while retaining completed history, interrupted Turns, and unsent drafts without another model request. `AREAL_REOPEN_FORCE_GUI=1` uses Main SIGKILL. Source fixtures tie Main to the test runner through a lifetime connection, so runner death reaches the product owner-pipe cleanup chain. Optional `AREAL_REOPEN_REPLACEMENT_BIN=/absolute/verified/areal` replaces only the private path with another genuine Mach-O executable during window reopen, verifies the running engine remains unchanged, and restores the original bytes and timestamp. Without it, the runner changes only the timestamp.

When a Core observation connection closes unexpectedly, its project owner retries with backoff from 500ms to 30s, discovers a compatible running instance through `service status --instance`, and restores Thread/Task snapshots, subscriptions and notification baselines through atomic `areal/thread/observe`. Observation recovery does not rebind the tool host. Only an explicit native-page claim reads authoritative state and attempts `thread/resume` binding for an idle Thread, subject to Core host-conflict checks. Recovery does not submit tasks again, synchronize Provider/MCP configuration or execute configuration revision barriers. Retired connections lose permission to update projections through messages or asynchronous results. Explicit stop, adapter shutdown, a stopping Core or an incompatible deployment fingerprint blocks automatic recovery; reconnection requires an explicit action.

The observation connection between GUI Main and its desktop backend also retries discovery and authentication of a compatible backend with backoff from 500ms to 30s after an unexpected disconnect, or when startup times out before the backend becomes ready. Recovery restores snapshots and notifications only: it never starts or restarts the backend/Core, retires an incompatible service, or replays commands with unknown outcomes. Explicit stop, an unconfirmed stop, persisted stop intent, a stopping service, and GUI shutdown block automatic attachment. Incompatible versions and other nonrecoverable errors retain the explicit reconnect action. `pnpm --dir clients/gui run test:service-connection` covers late readiness, unknown commands, identity changes, and stop boundaries over real WebSockets.

`@areal/workbench/desktop-contract` shares desktop command names, scopes, boundary input shapes and error fields. Thread configuration has concrete parameter types; other commands still rely on runtime scope validation. Main retains IPC sender validation. Core owns nested configuration and execution rules. String or numeric `code`, `submissionUnknown` and `requestId` pass through the adapter and Main so the UI can reconcile unknown outcomes.

Main owns native previews by project/Thread, with at most eight native Pages per window and four logical Pages per Workspace. Idle LRU eviction excludes executing, transferring, visible human, prepared-plan and file-handoff Pages; creation is refused when no candidate exists. Hiding retains a Page; archiving a thread, hiding a project and exiting the window release its WebContents. Late show requests cannot recreate invalid owners. Eviction retains the same Page shell URL/title and reports state loss; reopening advances pageGeneration. Navigation history and page memory are not guaranteed to survive, and unknown operations are never replayed automatically. Sibling Pages share a temporary Workspace Session, cleared after its last reference is released; different Workspaces are isolated. The limit bounds native Pages, not total Electron process memory. Previews expose no preload, Node or product bridge.

The adapter retains credential encryption, subscription forwarding, and mobile pairing, without another Agent loop. The subscription transport's local capability and fixed loopback port persist in a mode-0600 file under a private directory; upstream account/API credentials use OS secure storage. Adapter exit interrupts active forwarded HTTP responses. Stable transport identity supports subsequent requests, not uninterrupted streams through crashes. Window close retains the adapter; application Quit stops it after its owned engines settle.

The macOS package gives `AReaL Harness Service.app` a separate application identity. Reopening from Finder after foreground exit starts the GUI, which reuses the adapter and exposes deployment changes through explicit update; background notifications launch the main application entry. `gui-package` only stages a macOS arm64 candidate, defaulting to the already-built debug Core; installation packages use release Core as shown above. Candidate outputs include an `.app`, ad-hoc ZIP and DMG, dependency inventory and Core integrity manifest, and do not establish package acceptance. `sign:mac` uses an independent copy for Developer ID signing, app/DMG Apple notarization, stapling, Gatekeeper, and general desktop plus model-selection acceptance. Deliver its final ZIP/DMG after those checks pass. Use fresh output directories and bind the bundled Core revision to the final fix commit. Candidates have no automatic-update configuration; signing and notarization do not publish. See the [release guide](../../docs/development/releasing.en.md#gui-releases) for production publication and the update channel.

When staging a candidate package, `AREAL_GUI_CORE_BUNDLE=/absolute/core-bundle` can reuse a frozen Core bundle. Packaging still verifies embedded component hashes, and releases require a `release` Core. This setting only selects packaging input.

`make gui-smoke` runs real Electron/Core/Runtime against a deterministic local HTTP model with native sandboxing enabled. The project picker is injected with an isolated temporary workspace. Local model requests connect directly over loopback, preserving and merging existing `NO_PROXY` / `no_proxy` entries. Screenshots and `manifest.json` remain in the printed temporary directory; the manifest records Core binary checksums before and after the run and any failure reason. Set `AREAL_GUI_EXECUTABLE` to the absolute installed app executable for package testing; that mode uses bundled Core instead of an external binary. Real account login, paid models, other operating systems, and signed distribution require separate acceptance.

Finish Core builds before starting desktop smoke tests that use that binary, and do not relink it during acceptance. Model-selection smoke waits for saving and the Core model-selection state before the next action; GUI CI runs it and uploads logs, screenshots and manifests. On Core model-configuration child-process failure, the background service log preserves the operation, exit code, signal and timeout classification without recording secrets or the full environment.

`pnpm --dir clients/gui run test:conversation-derivation` preserves the complete RPC record and actively performs a real `trajectory/status` query during the measured bring-back interval. Bring-back assertions exclude only this exact read-only background query; retry, send, configure, queue and steer commands still fail the check, and related-discussion navigation additionally permits only `side/list`.

`pnpm --dir clients/gui run test:connection` covers real Core disconnect recovery, concurrent operations, retired connection messages and explicit shutdown. `pnpm --dir clients/gui run test:architecture` uses real Electron IPC to cover contract rejection, error-code forwarding and native preview eviction, crash reconstruction and owner release. ## Installation and updates

Formal macOS arm64 releases use a DMG for first installation and a ZIP for automatic updates, with Developer ID signing and Apple notarization. Verify the matching release's `SHA256SUMS`, drag the app from the DMG to your chosen installation directory, and open it while following macOS security and privacy prompts.

Before upgrading, back up GUI data (normally `~/Library/Application Support/AReaL Harness GUI`), shared configuration in `~/.areal`, and custom project data. Downloading keeps tasks running. After native validation, installation waits for active tasks, queued input, and backend operations to settle safely before stopping the backend and handing replacement/relaunch to the system. If stop acceptance is unknown, inspect the original backend resources without submitting installation again. Retry download/validation failures; if the app does not reopen after system handoff, open its original installation location and check the version. Reverting the app does not downgrade data: restoring an older app may require its matching backup. Credentials keep their existing secure-storage identity; directory backups do not imply keychain portability between machines.

Previews are manual ad-hoc installations without Developer ID distribution signing or notarization, and do not advance the formal update channel. Use isolated data or make a backup first. Older formal versions may not read preview data; moving from preview to formal requires manual installation and separate validation. Do not disable security protection or clear quarantine attributes to bypass system rejection.
