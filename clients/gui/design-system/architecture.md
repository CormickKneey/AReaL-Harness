# GUI 设计系统实现与准入

`R-ARCH-001` 本文件定义 GUI v1 实现职责与阶段准入。共享设计原则、意图、Token 地图与决策从 [Design Docs](../../../design/README.md)进入；当前 GUI 落地范围见[候选交付](../../../design/archive/gui/delivery.md)。源码事实、目录原型、计划中的 Base 和题目实验分别标明；不以文档完成代替 Base 或视觉验收。调研依据见 [automation.md](automation.md)。

共享知识与平台职责见[设计系统架构](../../../design/architecture.md)，下一轮产品建设见[建设计划](../../../design/roadmap.md)。整体候选与真实路径迁移仍按各自条件准入，不由文档整理自动通过。

`R-ARCH-002` 2026-10-24 按 [D-004](../../../design/decisions/004-local-ui-package.md)采用私有 @areal/ui 包的首批闭环：源、生成 CSS/主题、控件、类型/文档与 Agent 索引、独立示例及守卫。共享控件与组合的包化范围、生产适配和验证边界见[组件迁移](../../../design/archive/gui/component-migration.md)。业务页面与平台所有者继续保留；包化不自动提升Base准入。

## 目标与质量场景

`R-ARCH-003` 目标是让 Agent 把页面需求映射为已有设计决策，而不是为每页重新决定字体、颜色、控件、分组和状态反馈。架构先固定决策的所有者，再由 Base 提供可用实现，最后用独立题目检验规则是否足够。

| 变化 / 条件 | 应发生的结果 | 如何判断 |
| --- | --- | --- |
| 同类设置增加一个字段 | 调用方填标签、值与动作，选择已有控件/设置组合 | 不复制控件 CSS；模式合同覆盖必要状态 |
| `R-ARCH-004` 调整某个公共语义角色 | 在生产数值/主题所有者改变；合法消费者共同获得变化 | 单一改值点，偏好与主题覆盖保留，代表状态可验证 |
| `R-ARCH-005` 长标签或字号增长 | 公共布局约束决定换行与动作落位 | 宽窄条件下动作可达；不用逐页负 margin 或缩字号修补 |
| 做题暴露共性偏差 | 归因到规则、Token、组件或组合的唯一所有者 | 修改 Base 后原题复验，再用另一题确认没有只适配原题 |

`R-ARCH-006` 架构初稿先于 Base 和题目交付；当前候选的具体准入、探索题与边界见[Base](base.md)，不以目录生成器替代运行验证。

## 分层与所有权

`R-ARCH-007` 这是职责分层，不要求每层各建一个包。运行期依赖沿现有组件组合向下，规则与证据作为开发期输入；Core/Runtime 的执行、权限和历史权威保持原位。

| 层 | 拥有什么 | 输入与输出 | 不拥有什么 |
| --- | --- | --- | --- |
| `R-ARCH-008` 设计依据与决策 | 用户约束、参考来源、适用条件、采纳理由与例外 | 外部参考/观察 → 明确规则和待决项 | 不从参考图片直接覆盖生产值，不承载业务功能定义 |
| `R-ARCH-009` Foundations / Token | 文字、表面、状态、尺寸、形状与动效的语义角色及主题/偏好关系 | 生产基础与运行期偏好 → CSS 角色 | 不拥有页面内容，不让每个页面注册一套同义值 |
| `R-ARCH-010` Primitives | Button、Select、Switch、Input、Dialog、Feedback 等有限变体及键盘/焦点行为 | 语义 Token + 参数 → 基础交互控件 | 不发业务请求，不读取凭据，不判断权限结果 |
| `R-ARCH-011` Patterns | 设置分组/行、输入区、决策卡、长文本和过程等组合约束 | Primitives + 业务插槽 → 一致的结构和状态呈现 | 不接管 Core 状态机，不把所有页面压成万能表单 |
| Product surfaces | 任务内容、业务状态映射、真实动作绑定 | Patterns + 原业务所有者 → 用户页面 | 不重定公共颜色/字号/控件样式，不复制提交和恢复权威 |
| `R-ARCH-012` Validation / evidence | 声明检查、生成一致性、交互结果与视觉证据 | 固定来源/状态/条件 → 可追溯报告和待修项 | 不反向生成生产数值，不自动接受新视觉基线 |

`R-ARCH-013` 包内Worktree领域组合位于`packages/ui/src/worktree`，与conversation并列，依赖core控件；core不可反向依赖领域层。五个组合通过原Worktree业务适配接入，状态与操作权威保持原位。短时通知采用core层NotificationToast及原ToastHost通道，等级颜色来自既有语义角色。

`R-ARCH-014` 工作台层位于`packages/ui/src/workbench`，拥有壳层、面板结构、设置导航、任务行及资源范围/空态。面板注册、拖拽身份、关闭守卫、保活与原生资源生命周期归宿主；层级不可反向依赖renderer。

系统级目录 `registry.json` 是上述角色、组件与模式的索引。它只引用数值源和实现，不是新增的数值层，也不承担渲染引擎职责。

## 与现有所有者的映射

当前数值与偏好所有者见[Token 地图](../../../design/foundations/tokens.md#每类值在哪里改)，组件与生产入口见[目录](inventory.md)，生成与检查入口见[自动化](automation.md)。这些索引分别引用实际源码，不在本页复制接线状态表。

`R-ARCH-016` 颜色、字体、间距等的实际优先级继续由现有 CSS cascade、主题适配与外观应用决定。Base 阶段必须以代表控件的 computed style 核对整条链，不能只因为变量存在就宣布统一。尚未观测的跨平台与自定义主题结果保持缺口。

## 数据合同与权威

| 数据 | 可编辑的真源 | 派生物 / 消费者 | 维护规则 |
| --- | --- | --- | --- |
| `R-ARCH-017` 精确设计值与动态派生 | 首批包内 tokens.json/theme.ts；未迁入 CSS、主题和偏好所有者 | 生成 CSS、默认主题输入、生产控件及 computed style | 迁移时删除旧可编辑定义，保留宿主偏好和未迁入边界；不从生成物反写源 |
| `R-ARCH-018` 角色/组件/模式目录 | registry.json | catalog.ts、inventory/patterns 的生成区块 | 同源生成，check 拒绝过期/手改；不从生成物反写源 |
| `R-ARCH-019` 模式的使用原则与准入 | foundations / patterns / governance 中的人工区块 | Agent、实现与评审 | 结构事实放 registry，使用理由放规则；同义规则只保留一份 |
| 页面实现合同 | surfaces 中的数据 | 具体实现与状态验收 | 引用模式、组件、来源、状态和条件；不是执行 DSL |
| `R-ARCH-020` 做题输入与评判依据 | 后续独立的题目包与 rubric | 实现者只读题目；评估者读题目、参考和实现 | 当前预览合同不是独立题目；不将答案嵌进生成步骤 |
| `R-ARCH-021` 原始运行证据 | 本地 run manifest、原图与日志 | 对照报告及规范的采纳结论 | 绑定实际版本和条件，保护私有数据；不能自动成为新基线 |
| `R-ARCH-022` 视频候选与核查裁决 | 原始模型结果、本地核查记录；格式见[结构化流程](structured-flow.md) | 既有所有者修复及规则更新 | 候选为辅助观察，不拥有执行、设计值或准入权；核查通过后才进入相应设计决定 |

`R-ARCH-023` `schemaVersion` 表示数据格式；未来的 Base 版本表示一套可复验的规则与生产实现。二者不能混用。`schemaVersion: 1` 和目录提交不等于 Base v1 已冻结；当前 Base候选版本在 registry 的 baseCandidate 中维护。

## 结构化数据如何约束实现

任务输入表达意图、内容、状态、条件及所选模式；设计目录把这些选择限制在已有角色和组件中；React 实现仍通过真实组件组合完成。让已有 `SettingsSelect` 决定二值/多值控件，让设置行拥有换行和对齐，比让每页按 JSON 重新生成一套控件更稳定。

`R-ARCH-024` 结构化合同负责保留“选择了什么”，类型/校验负责排除可判定的非法选择，组件与组合负责运行呈现，独立取证负责判断实际效果。单靠 JSON 完整性无法推出高保真。

`R-ARCH-025` 不建设通用页面 JSON 渲染器，不创建第二套 Token 编译器，不把所有 JSX 改成配置驱动。将来只有多个真实消费者需要同一能力时，才扩展公共接口；业务差异通过内容、插槽与有限变体表达。

## 自动化分工与约束强度

检查范围与静态限制由[自动化](automation.md#增量设计检查)维护；证据能证明的范围由[治理](governance.md#证据分层)维护。

`R-ARCH-026` 截图是反馈传感器，不能成为逐页设计的唯一机制。对确定性结构约束用代码检查；对视觉质量用受控比较；对未决产品语义保留明确决策，避免把审美猜测写成 lint。

## 方案取舍

| 方案 | 收益 | 代价 / 结论 |
| --- | --- | --- |
| 只扩写规范 | 上手快 | 实现可绕过，目录/示例会漂移；不足以单独达成目标 |
| `R-ARCH-027` 全量替换为独立设计包、DTCG 全生成或通用页面 DSL | 来源集中、可跨端转译 | 共享展示逐批迁入同源私有包；本轮不引入DTCG编译器/页面DSL，用户偏好与业务边界保留 |
| `R-ARCH-028` 复用生产所有者，补职责分层、单源目录、有限组合及独立验证 | 可增量落地，已有公共控件立即受益 | JSX 依从与视觉质量仍需单独检查；作为当前方案 |

`R-ARCH-029` 若未来出现多个独立运行端必须消费同一设计源，再复审 Token 编译与跨端 recipe；不能仅因参考项目采用就提前迁移。

## 阶段及准入

### A：架构

`R-ARCH-030` 完成条件：分层、来源、所有者、依赖、数据合同、自动化边界和后续准入均明确；上述质量场景各有修改与验证位置。交付本文件及现有仓库架构导航。架构文档不声明某种视觉已经获批。

### B：Base 设计系统

在该架构下挑选最小但完整的基础切片：生产字体/色彩/空间/形状角色，常用控件的有限变体，至少一个真实设置组合和一个内容/决策组合。沿现有所有者补齐缺口，不重新绘制全产品。

`R-ARCH-031` 准入条件：每个角色有唯一生产来源；组件有明确任务、默认/交互/异常状态；主题、字号、宽窄、键盘和 reduced motion 的代表条件有证据；未覆盖项列明。登记为 Base 的是“规则 + 实现 + 验证边界”，不是只有一个目录 ID。

### C：固定题目与模拟页面

`R-ARCH-032` 先固定题目、内容、初始值、操作后状态、viewport 和评分依据，再用冻结 Base 实现一个新的模拟页面。只复用现有组件与模式，允许的局部差异来自任务内容。模拟页属于开发预览，不能进入生产路由或连接真实业务。

`R-ARCH-033` 实现输入与评判材料分开：要检验 Base 是否足够时，实现者不读取目标效果截图或详细参考实现；评估者按同条件对照。当前同会话已看过的预览不能声称是盲测，新页面的试运行也不能当作整体泛化证据。

### D：归因并改进

`R-ARCH-034` 将偏差分为规则缺失、规则含糊、组件/组合缺陷、未遵守规则、任务或参考含糊。前三类回到共享所有者，未遵守规则修实现或检查；任务歧义修题目，不硬塞进全局规范。修订 Base 后复跑原题，并保留另一种真实任务用于检查是否过拟合。

`R-ARCH-035` 阶段按 A → B → C → D 推进。当前已完成有限 Base 冻结及[固定输入的独立复用与归因](../../../design/components/reuse-result.md)，历史探索题仍保留各自边界；取证只在来源、Base 和题目明确后开展，用户要求长期保留的 CDP 实例不因阶段切换而关闭。

## 按用户交互组织

`R-ARCH-036` 基础语言 → [交互模式](interactions.md) → 业务组合 → 验证。八类交互族定义用户意图和响应约束；P-* 保留组合及生产所有者。规则分必须、默认、可探索；具体数值仍归生产 token。registry 只索引交互族、规则与组件，目录生成器校验引用；不生成页面或执行状态。新增分类不扩大 Base 准入。
