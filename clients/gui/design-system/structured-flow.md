# 结构化数据到高保真实现

本页定义 [架构阶段 B/C](architecture.md#阶段及准入) 的 v1 合同。先明确架构，再形成有证据的 Base，最后固定题目与模拟页面。当前设置控件合同描述已有预览；设置迁移和内容/决策合同描述候选探索题，均不是盲测或已批准视觉基线。

本页是Agent设计、修改和验证页面的默认执行入口，采用已选定的视频辅助核查路线（B路线，与架构阶段B的Base准入不同）。本流程把“要做什么、按什么做、如何判断相符”固定下来。输入是设计意图和受控引用，输出是生产组件的组合及可追溯证据；页面业务状态仍由原所有者管理。它不是将截图铺在页面上，也不是让 JSON 绕过 React/Core 的执行边界。

## 两类数据

[registry.json](registry.json) 是系统级目录，拥有 Token 角色、组件 ID、模式 ID 和最低状态合同；不存数值副本。[surfaces/settings-controls.json](surfaces/settings-controls.json) 是当前预览的页面级合同，引用同一目录。[设置迁移合同](surfaces/settings-reflow.json)与[内容/决策合同](surfaces/decision-transfer.json)演示新内容对已有组合的引用。[对话信息流合同](surfaces/conversation-flow.json)固定逐步投影题的规则引用和检查点，目标为ConversationFlowExercise；本地运行和公共视觉基线分别报告，后者保持pending。修改规范或增加公共组件时维护目录；普通页面变更维护所属合同，不复制全系统规则。

## 页面合同字段

| 字段 | 决定什么 | 校验边界 |
| --- | --- | --- |
| schemaVersion / id | 合同版本和稳定身份 | v1、唯一 ID |
| intent | 用户需要完成的任务 | 必填，语义仍需评审 |
| pattern | 页面组合模式 | 必须在 registry 中 |
| target / runtime | 实现入口与 component-preview / desktop / remote 边界 | 路径存在、runtime 合法；不代表已运行 |
| reference | 已有生产参考，或选定 screenshot / figma 视觉目标 | 代码路径存在；视觉引用必须明确，不能用 nearby option 替代 |
| rules（模式声明时必需） | 引用模式要求的全部规则ID；语义只在模式的ruleSource文档中维护 | ID无遗漏或虚构，规范有唯一定义；不证明JSX遵守 |
| slots | 页面各槽位所用组件 ID | 模式槽位完整、ID 已登记；不是 JSX 执行器 |
| states | 每个状态的到达条件及可观察结果 | 模式必需状态不能缺；实际交互由独立验收确认 |
| conditions | 主题、字号、宽窄与 reduced-motion | 声明本次适用条件，不意味着跑过所有组合 |
| invariants | 跨状态保持的约束 | 非空，语义由评审核对 |
| evidence | pending / captured / compared、artifacts 与 gaps | 非 pending 需路径、SHA-256 和状态；元数据完整不等于视觉通过 |

模式的`ruleSource`与`rules`在registry中成对登记；文档用单个`规则ID`后接中文冒号定义正文。页面合同完整引用ID，不复制规则文字。states可以是多条独立状态轴的验收检查点，不能据此新增Core枚举或全局状态机。

所有路径相对 `clients/gui/`，截图等本地材料的路径仅放本地证据副本；公开合同保留稳定来源、采纳结论与缺口。当前样例明确标记 pending，不能作为 Codex 对齐或 AReaL 运行通过证明。

## 执行顺序与每步完成条件

| 步骤 | Agent执行 | 本步完成条件 |
| --- | --- | --- |
| 1. 固定题目与合同 | 写用户任务、问题ID、模式/规则、target、slots、states、conditions与可反驳的验收条件；从目录确定生产所有者。合同新增或修改时运行`verify:design`检查引用。 | 有可到达的起点/主操作/异常或返回路径；参考选择明确，设计值与业务状态各有唯一所有者。新页以相近生产组合为实现起点；缺少模式/变体时按变更准入补齐真实消费者的最小能力。 |
| 2. 固定参考与当前运行 | 复用适用的run manifest、原图、事件、阅读位置和录像；缺少会改变实现的观察时，补一条有界旅程。参考与实现分别登记版本、条件和身份。 | 能将每段媒体定位到对应run与状态；列出条件不匹配、采样间隙和时钟误差。动态结论有过程证据。 |
| 3. 视频提名候选 | 按[视频分析提示词](templates/video-analysis.prompt.md)，向已授权的视频工具提供限定材料和[输出schema](templates/video-analysis.schema.json)。分析者输出可见事件、候选差异与建议复核时间段，保留请求、原始结果、实际模型/采样限制。 | 原始输出可读取，候选ID唯一、媒体引用存在、时间范围合法且有不确定性；视频未成功读取时明确标记，不能从brief补造事件。 |
| 4. 关键帧与日志核查 | 按候选边界、冲突或重要动作查看关键帧总览，并放大相关原图；核对原始动作、人工展开、回看/跟随、父子独立状态与运行重置。 | 每个候选都有原图/事件引用或明确缺口；按[差异筛选准入](governance.md#差异筛选准入)分开观察与推断，并说明可比较维度。 |
| 5. 筛选并定位所有者 | 在现有run报告中裁决候选；缺少载体时复制[核查模板](templates/evidence-review.template.json)。选当前任务内已确认的缺口，写规则ID、生产所有者、原因假设与关闭条件。 | 每条候选已标记采纳、拒绝、保留差异或待补证据；只有达到准入条件的项进入实现。没有成立缺口时，记录无需修改并结束该问题。 |
| 6. 实现最小切片 | 沿既有Token/组件/组合修复确认差异，页面只填内容与合法动作。新公共状态进入原生产预览；验收标记留在DOM或实验控制台，产品消息只呈现用户任务所需内容。 | 改动可映射到采纳项与原所有者；没有并行组件、数值副本或由fixture步骤推导的新业务状态机。 |
| 7. 重放与比较 | 在最终源码/构建上重放受影响的全部状态，按原关闭条件检验行为、数据结果与画面。使用真实操作和可观察到达条件。 | 原失败方式已有对应证据；重访、异常、键盘、主题/字号/宽窄按合同选代表组合。失败、未覆盖与通过分开，不用类型检查替代用户路径。 |
| 8. 更新与交付 | 将通过验证的设计决定写回唯一规则位置；按需更新surface、inventory及registry，后者有变化时同步派生物。审阅owned diff。 | 采纳项关联最终验证与规范变更；未关闭项仍可见，交付标明fixture/桌面/安装包边界。Base版本和视觉基线按原准入处理，不随文档或模型产物自动提升。 |

默认顺序是先核查再改动，验证后才将设计决定写为已确立规范。若步骤1发现原规则含糊，先把拟议规则和验证条件标为候选，再实现/复验；源码已经存在的行为不因视频模型误判而重建。

### 按任务裁剪

- 动态、异步、多面板、滚动、完成收敛或恢复路径：执行相关完整旅程，按[动态关联证据](governance.md#动态信息流的关联证据)关联事件、阅读与录像；终态截图不足以关闭动态问题。
- 静态文案、沿既有规则的小改动：可复用仍适用的原图与运行证据，记录为何适用；视频分析标记`skipped`及原因，直接核查受影响状态，不强制调用外部模型。
- 新页面：先用已有模式和Base组件做最小完整任务，再按同样条件取证；新增布局或状态需要明确问题与准入，不能把独立生成的新页面当成已批准设计系统。
- 视频模型不可用、未获当前素材的外发授权或采样覆盖不足：标记`unavailable`或待补证据，使用已授权的原图、实际交互及日志继续核查。素材选择、普通模型认证和参考实例保留遵从任务授权；工具名、模型版本或High强度均不是正确性证据。

按状态行为 → 布局 → 组件 → 表面样式排序差异。模板是设计期交换格式，不是运行期页面DSL，也不自动批准视觉基线。

核查模板初始为pending/needs-evidence；在既有报告中使用相同字段即可。证据引用填原manifest中的runId、frame/event ID和哈希定位，已有身份/版本/条件继续归原manifest。`comparison.state`用matched/mismatch/unknown描述状态是否可比，`basis.kind`用reference/rule/product-choice/unknown标明依据；最终裁决与实现验证状态分别维护。只有实际通过的规范变更才加入`normUpdates`并列规则ID、唯一文件、理由及验证引用；具体裁决语义见[差异准入](governance.md#差异筛选准入)。

已有runner和报告可保留自己的字段；能覆盖上述完成条件时只补缺项，不另建一套账本。模型供应商封装的JSON/NDJSON保留原件，提取其中的结构化结果另存，不能覆盖原始答复。

## 截图取证方案

先把参考和实现分别登记为 run；引用原图及 SHA-256，记录应用版本/源码、dirty 状态、viewport/DPR、主题、字号/字体、内容与交互状态。每帧绑定合同 ID、状态 ID、进入动作和可见完成条件。

优先采集公共控件的代表状态：设置组默认、二值选择、菜单打开、disabled、busy、失败与待确认；随后是对话过程/最终回答、长文本与决策卡片。不同主题、字号与宽窄用代表组合覆盖，不能凭一张总览声称全矩阵通过。Codex 参考只观察展示，不推断其执行协议。

同一帧比较包括：整体层次与区域比例、字体/换行、间距/对齐、语义色/状态、资产/图标和实际文案。全图细节看不清时追加区域图；归一化密度与裁剪后再比较。截图保存不等于 QA；构建成功也不替代同状态视觉比较。

当前阶段先建立自动化数据链和取证合同，截图采集不作为生成步骤；更不自动接受新基线。当前合同的视觉目标和运行证据缺口保留为 pending。

动态信息流按[动态关联证据](governance.md#动态信息流的关联证据)追加事件、阅读锚点及录像关联。任务合同同时写出运行条件和读者动作，例如“正文继续增长时向上回看”，不能只列一个busy截图。真实模型用于观察参考；实现复验可用固定输入事件序列控制外部到达顺序，但必须通过生产组件处理，不直接注入预期的展开或跟随结果。

## 交互分类输入

先按[用户交互模式](interactions.md)写[设计时简报](templates/interaction-brief.json)：主要交互族、支持路径、must/default 规则、生产组件、例外及可观察结果。随后执行本文件既有 B 流程。视频用于提名变化；静态设置复用有效参考和同态图，不为分类齐全而录制无用视频。新分类的目录合法性、行为、视觉和平台覆盖分别报告。
