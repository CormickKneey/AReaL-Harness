# Desktop API: areal.core.v1

This contract extends [Core WebSocket](core.en.md), separately from Runtime JSONL and [CLI stdio](claude-cli.en.md). Full requests, responses, notifications and persistent types are in [areal-core-v1.json](../../schemas/areal-core-v1.json). Typed AReaL requests reject unknown fields; Codex compatibility methods retain their pinned wire contracts.

`make desktop-schemas` exports package and hook DTOs from their Rust types and includes the [pinned Codex 0.162.1 plugin contracts](../../upstream/schemas/codex-plugins-0.162.1/methods.json), whose [provenance](../../upstream/schemas/codex-plugins-0.162.1/provenance.json) identifies the source of each contract. Generation requires paired request/response schemas and every advertised notification. The example client additionally verifies coverage against the running Core's capabilities.

Web/PWA Remote uses a separate restricted [areal.remote.v2 contract](remote-control.en.md), mediated by the desktop background adapter with current device authorization checks. It exposes neither a generic entry to this API nor local Bearer tokens; Remote design and implemented scope are identified separately.

Thread snapshots and Item notifications accept the optional `agentMessage.phase` field; see [Core message phases](core.en.md#agent-message-phase) for lifecycle, examples and legacy compatibility. This additive response field keeps `areal.core.v1` unchanged.

## Authentication and connection

Product servers listen on loopback and authenticate WebSocket/Blob requests. Trusted Main reads its Bearer token from authFile in ready metadata; Renderer receives neither that file nor model credentials. Built-in Web uses a separate HttpOnly, SameSite=Strict session cookie and validates Origin; see automatic local login below.

The auth file `{version:1,principals:[{id,token,permissions,threadIds?}]}` requires mode 0600. Permissions are observe/interact/manage/tools; explicit threadIds limit observation and interaction. Client names and Thread IDs are not authentication.

Use initialize → initialized → areal/capabilities (optional apiVersion). Request IDs are independent in each direction; item/tool/call is a server request requiring a response. Replace the baseline through thread/resume. See [Core](core.en.md) for subscriptions, queues and backpressure.

<a id="browser-auth"></a>
### Browser login

- `POST /areal/auth/bootstrap`: a trusted local client supplies `Authorization: Bearer <local token>` without Origin; success returns `200 {code,expiresIn:60}`. Cookies cannot mint codes; requests with Origin receive 403.
- `POST /areal/auth/bootstrap/exchange`: the page sends JSON `{code}` with an Origin exactly matching the service. Bodies are limited to 1 KiB and unknown fields are rejected. Success returns 204 with a session cookie. Invalid, expired, consumed or other-instance codes return 401; missing or mismatched Origin returns 403.
- `POST /areal/auth/session`: manual Bearer login remains available, returning 204 with an independent session cookie. Existing cookies cannot renew a session. Any supplied Origin must match the service.

Codes have 244 bits of random entropy, expire after 60 seconds and are consumed atomically once. The CLI opens `/ui#bootstrap=<code>`; fragments never enter HTTP request targets. The page uses `history.replaceState` to remove the fragment from the current history entry before exchanging it through POST, without localStorage/sessionStorage. Failed automatic login prompts another `areal web` invocation or manual login. Authentication responses use `Cache-Control: no-store`; clients disable proxies and redirects. Long-lived launcher tokens never enter URLs, service descriptors, logs or cookies.

Cookies are named `areal_session_<origin digest>`, omit Domain and use `HttpOnly; SameSite=Strict; Path=/; Max-Age=3600`. Transport is restricted to HTTP loopback, so the HTTPS-dependent Secure attribute is omitted. Names distinguish local ports; cookies are not an isolation boundary against untrusted processes on the same host. Independent sessions inherit the original permissions and threadIds. The server stores SHA-256 digests of codes and session IDs and enforces a one-hour absolute lifetime: HTTP/new WebSocket authentication is rejected and existing browser connections close, without cancelling background tasks. Restart invalidates all codes and browser sessions. Each service retains at most 64 valid codes and 1024 valid sessions; capacity returns 429 without evicting existing sessions.

Compatibility: Bearer clients and the authentication file format are unchanged. Legacy `areal_session=<long-lived token>` cookies are rejected; run `areal web` again or sign in manually after upgrading. `areal web --json` preserves its descriptor and neither opens a browser nor mints a code. Request/response types are browserBootstrap / browserBootstrapExchange in [local-service-v1.json](../../schemas/local-service-v1.json).

## Submissions, configuration and recovery

requestId is a durable business key; RPC id only correlates responses. Identical identity, method, key and normalized parameters return the original result; changed parameters conflict. Each Thread permits 1024 receipts; management logs permit 4096. Exhaustion rejects instead of forgetting keys. Accepted management records without results become UNKNOWN after restart and are not reexecuted.

`areal/turn/submit` atomically admits ordinary conversation input using `{requestId,threadId,expectedConfigRevision,intent}`. The tagged intent is `{type:"message",input}`, `{type:"continue",expectedTurnId}`, or `{type:"edit",expectedTurnId,itemId,input}`. Continue accepts no text. Support requires both `features.ordinaryTurnSubmit=true` and the advertised method. Under the lifecycle, Thread, and ordinary ownership locks, Core reads receipts before checking configuration, ownership, archival, compaction, cancellation settlement, and UNKNOWN. Task, Goal, Side, and task management conversations retain their existing entry points.

Edit requires `features.editLastMessage=true`. It accepts only the last user message in an idle ordinary conversation with no pending/running queue items. `expectedTurnId` must match the latest Turn, including any continuation; `itemId` must match the last non-continuation user message. Core hydrates archived history, removes that message and all subsequent items/Turns, invalidates the context checkpoint, and prepares a replacement Turn. Validation and persistence complete before activation, in one snapshot with the receipt; rejection preserves history. Earlier items in a steered Turn remain. File and external effects remain. After commit, `areal/thread/edited {threadId,thread}` explicitly replaces the client history baseline before `turn/started`; ordinary partial Turn events still merge items. Lost replies use the original request receipt, never a separate rewind or automatic resend.

Message preserves the submitted input. A normally active Turn queues it at the tail. An idle Thread without pending input starts a Turn directly. With pending input, Message appends at the tail and resumes the queue; Continue resumes the existing queue. Both respect the authoritative FIFO order. Continue without pending input creates a new Turn in the same Thread, records `continuedFromTurnId`, and uses a visible continuation instruction with history and the current workspace. Its anchor must be the latest `interrupted` Turn, or a `failed` Turn with an explicit interruption fact or Core recovery UNKNOWN evidence. Ordinary model failure and completed Turns do not qualify. Uninspected tool, Hook, or plugin UNKNOWN and unresolved resource cleanup still block execution.

Direct execution returns `{turn}`. Queued admission returns `{queueItemId,queueRevision,configRevision}`. Continue has a null `queueItemId`; Message identifies only the newly submitted item. Core persists the Turn, queue, and receipt in one snapshot before activation or scheduler notification. `areal/request/read {threadId,requestId}` reads the receipt for this method. A lost response or failed client journal cleanup retains the original key and never replays with a new key. Basic `turn/start` and durable `areal/turn/start` cannot bypass retained pending or running items.

turn/start/enqueue take `{requestId,threadId,input,expectedConfigRevision?,interactionMode?}`. Queues retain at most 128 historical items with frozen configuration. Only success advances automatically. Stop/failure/UNKNOWN/restart/drain pauses the queue until explicit resume. After timeout, query request/read or authoritative state rather than assuming no side effects.

Optional `turn/start.admissionGuard: {configRevision,ordinarySession:true}` checks the configuration revision and current ordinary-session ownership atomically before freezing configuration and persisting the Turn. Managed children, active or settling Goals, queued/running/waiting Task Runs and unsettled workers reject admission. Fully settled history or a future schedule alone does not reserve the Thread. Archived sessions, paused or nonsettled queues and existing busy/UNKNOWN/tool-host checks remain barriers. Core retains the Task reservation lock through durable activation. This guard is unavailable on enqueue; `ordinarySession:false` is invalid. Support is declared by `features.turnStartAdmissionGuard`.

Optional `thread/start.admissionGuard: {ordinarySession:true}` checks the resolved explicit/default Profile before creating the Thread or starting a Workflow. Workflow-bound Profiles return argument error `-32602` with `UNSUPPORTED_PROFILE:` in the message. Accepted guarded creation replays return the original Thread without attempting Workflow startup. Support is declared by `features.threadStartAdmissionGuard`. Omitting either guard preserves existing local behavior; omitted fields preserve existing receipt digests. Receipt lookup precedes new guard checks, so an identical accepted request returns its recorded result rather than re-evaluating changed state.

`areal/thread/observe` returns `ownership: {kind: "ordinary" | "task", taskId?, runId?}` beside `thread`. `features.atomicObserveOwnership=true` guarantees ownership, snapshot and subscription are captured under the same Thread → Tasks locks. The predicate matches ordinary admission: active/settling Goals, managed/child Threads, queued/running/waiting Runs and unsettled workers are Task-owned; settled paused/blocked Runs, history and future schedules alone are not. Task/Run IDs require the existing Task and coordinator visibility rules; hidden or unbound ownership remains `kind: "task"` without IDs. If several Runs reserve the Thread, IDs identify only a unique Run bound to the current active/settling Goal; without such a Goal, only a sole eligible Run can supply IDs. Ambiguous ownership stays `kind: "task"` without IDs. This projection is not persisted in Thread.

`areal/queue/steer` accepts `{requestId,threadId,expectedRevision,queueItemId,expectedTurnId}` to atomically transfer a pending entry to the specified active Turn. Under one Thread lock, Core reserves steering capacity, validates the Turn and input, and persists the message, `steered` queue status and receipt together before notifying the executor. Rejection keeps the entry pending. Success returns `{queueRevision,queueItemId,turnId,itemId}`. Steering uses the active Turn model and mode; queue updates retain the original queued configuration. The same identity, request key and parameters return the recorded result; different parameters conflict. Query its receipt with `areal/request/read` and threadId. Unknown results are observed without automatic resubmission.

Composer edits queue entries in the main input after confirming a pause. Saving updates the original position and attachment references while retaining the queued model/mode; save or cancel restores the original draft. The previous unpaused state is restored only while the revision and pause reason still belong to that edit. External updates, deletion or UNKNOWN preserve the edit without implicit overwrite or state restoration. Existing unsent File drafts survive navigation within the current GUI process; no disk attachment cache is added. `pnpm --dir clients/gui run test:queue` checks the queue paths with isolated Electron/Core/Runtime and a deterministic HTTP/SSE model.

`EffectiveConfig.defaultModelRevision` is an optional opaque reference to a default-model snapshot. Desktop creation and explicit selection of the implicit service default pin this reference. Later parameter and permission changes preserve it. Generic sessions without desktop configuration still pin the default version when submitting a Turn or queue item. Explicit Provider selections retain their model and Provider snapshots. The model archive belongs to the data directory and contains no environment credential values.

At service startup, an older desktop session with an implicit model and no revision recovers the implicit revision from its last admitted Turn when that snapshot contains one. Core persists the recovered session configuration. Missing historical evidence remains unknown. Reading history neither reconfigures the session nor submits messages. Optional `modelName` and `resolvedParameters` in `thread/inspect` project the implicit model's safe name and effective parameters from the existing archive. Missing historical metadata produces null instead of the current default's name.

thread/configure requires expectedRevision and an idle, non-compacting Thread. resetModel=true clears the session model override to Profile/service defaults and cannot accompany a nonempty model. Omitted parameters retain values. `{}` resolves model defaults followed by Provider defaults. `parameters.reasoningEffort:null` clears the effort override. Clients must include other parameters in the same object to retain them; omitted fields resolve to defaults. Composer includes those parameters when resetting effort. A model default of high therefore still resolves to high. `selectedSkills` accepts `{id,revision}` Skill references; an empty array clears the session override and restores the Profile, and every reference must belong to the active Profile. features.modelReset advertises support.

`areal/thread/start` accepts `{requestId,agentProfile:{id,revision},cwd?,model?,parameters?,dynamicTools?}` and creates a Thread with configuration frozen from that Profile. Clients can pass the same reference with `--agent id@revision`; a separate Workflow selection is unnecessary. The Profile `workflow` field is an Agent property: creating the Thread starts it once and records the Workgroup ID and startup status in `desktop.workflowRun`; query the Workgroup API for live status. Retrying the same requestId or resuming the Thread does not start it again. A Workflow-bound Profile can only be selected when creating a Thread, not switched through `thread/configure`. A Profile without a Workflow does not require a Workgroup policy and can still use tools permitted by its `toolAllowlist`.

Each `areal/model/list` entry includes `parameters` resolved by Core from model and Provider defaults. `isDefault` marks the service default for new chats. An explicit Profile model still takes precedence. Before sending, Composer displays the concrete model and effective effort. An entirely absent effort displays "供应商默认"; explicit `none` displays "无". "使用模型默认" clears the current effort override without bypassing saved model or Provider defaults. A new chat retains choices only for its unsent draft and clears them after creation. History uses the session's current saved selection; existing Turn snapshots remain unchanged.

`areal/model/list` also returns the instance's `lastAcceptedModel`, or null: `{acceptedAt,model,modelId,reasoningEffort}`. `acceptedAt` is Core admission time in Unix microseconds; `model` is a provider model reference or null for an implicit service default, and `modelId` is the effective model name. A null effort differs from explicit `"none"`. Main-conversation `areal/turn/submit` and explicit user `areal/turn/start|enqueue` persist this record with the admission receipt in the same Thread snapshot, returning it in the response and retained receipt. Receipt reads do not refresh the timestamp, and background execution does not update it. Desktop aggregates these records across projects and persists the new-chat preference without owning existing conversation configurations.

Optional `parameters.reasoningSummary` accepts `auto` / `concise` / `detailed` for Responses only, merging Provider defaults with Thread overrides. Summary requests remain disabled when neither Provider/service defaults nor Thread overrides configure it. `areal/model/list.parameterCapabilities` includes `reasoningSummary` only for Responses providers; this advertises adapter support, not support for every upstream model or mode. See [Core reasoning progress](core.en.md#reasoning-progress) for events and parts.

options.readOnly narrows Scope write roots and networking. toolAllowlist narrows the Profile; preapprovedTools cannot remove mandatory deployment approvals and matches only the current tool name; preapproving a read tool does not exempt its hooks. maxModelRounds is 1–1024 with a handoff-only final round, not a team request budget. Profile/Workflow definitions use immutable id/revision pairs; Skill references do not freeze resource content, as described below.

`areal/model/list.reasoningEffortOptions` reports the existing HTTP adapter's accepted values (`none/minimal/low/medium/high/xhigh`; empty for other adapters). This does not guarantee support by every remote model. Composer reads these options from the catalog and submits parameters through the existing thread configuration path.

<a id="skills"></a>
## Model configuration hot apply

Shared services provide two narrow methods. Discover support from the current connection's `areal/capabilities.methods`. Only an authenticated `desktop-owner` with `manage`, `tools` and no Thread scope may call them. Observers, ordinary model clients and standalone Engines without a configuration controller do not have this capability. Requests cannot select a file path, supply Provider metadata or change arbitrary process environment variables.

| Method | Request | Purpose |
| --- | --- | --- |
| `areal/server/modelConfiguration/read` | `{requestId?,expectedGeneration?}` | Read the actual applied version or inspect the original request. |
| `areal/server/modelConfiguration/apply` | `{requestId,expectedGeneration,expectedApplied:{revision,sequence},targetRevision,credentials}` | Read authoritative configuration and apply it under Core's admission gate. |

`credentials` is a bounded mapping from `AREAL_CREDENTIAL_` names referenced by the target file to secret values. References are immutable additions; a different value for an existing reference is rejected. Old references remain available to existing tasks. Secrets exist only in trusted requests and execution memory, never in configuration, history, digests, logs or receipts. This endpoint cannot update ordinary startup environment variables.

The response contains `{serviceId,generation,applied:{revision,sequence},modelRevision,credentialStates,operation?}`. `applied.revision` identifies the committed whole configuration file; `sequence` increments after successful application within that generation. These differ from the default model's `modelRevision`. Startup assembly begins at sequence 0. Core checks the revision and configuration from one controlled file snapshot. It rejects stale targets, non-model deployment changes, active work and credential conflicts, without draining or restarting Core or Runtime. Existing Thread, Turn and queue configurations retain their original credential references.

`operation` identifies the original `requestId` and has state `running`, `applied`, `rejected` or `unknown`, with an optional redacted terminal `result` or `error`. Core owns accepted operations; disconnecting does not cancel a commit. Duplicate requests return their original result without publishing again. Inspect the original request after losing a response. In-memory receipts are bounded; a generation change or unavailable record does not prove failure and cannot authorize automatic replay. Clients may verify a new instance's current readiness without treating it as the old request's receipt.

Each Core applies and confirms independently. Known partial failures may trigger a file CAS compensation followed by application of the actual restored revision. Do not roll back while an earlier request remains unknown. External writes or newly admitted work may prevent compensation; retain actual applied versions and pending state. The GUI reports save completion only when every project confirms and the authoritative file still matches the target. File watching and explicit application share the applied baseline. Non-model settings retain the safe-restart boundary.

## Skill metadata and resources

Trusted deployment manifests accept skills as `{id,revision,root,metadata?:{name,description}}`, with root relative to the manifest directory. When metadata is omitted, registration parses only the bounded SKILL.md header without scanning attachments. Explicit deployments and discovery share the same on-demand read behavior.

`areal/skill/list` accepts either `{threadId}` or `{agentProfile:{id,revision}}`. Drafts can observe registered Profile metadata without creating a Thread or reading content. `areal/skill/read` accepts the same mutually exclusive contexts for draft previews of resources allowed by that Profile. Profile reads do not register Thread loading state; sending reads again in the owning Thread. Composer stores skill references and sources, reads SKILL.md before sending, and attaches it to the current message. Read failures preserve the draft.

Entries in `areal/skill/list` data add name/description; resources is always null instead of a complete resource inventory. available and resourceRoot retain their meaning. Initial model prompts include only names and bounded descriptions; agents call skill_read for full instructions.

`areal/skill/read` / `skill_read` reads current disk content on each call, with maxBytes of 1–8192 and offset/nextOffset pagination. sizeBytes is the file size observed when opened for that call. Resources may exceed 256 KiB; binary content uses dataBase64. Concurrent changes may produce inconsistent pages. See the [Skill guide](../guides/skills.en.md) for path restrictions and discovery warnings.

Compatibility: Skill revision no longer guarantees immutable content, and legacy skillHashes are ignored. Existing `{id,revision,root}` manifests remain valid. Trusted launchers must register historical references or they are unavailable. Auto-discovered revisions now hash metadata; persistence semantics for Profile/Workflow definitions and session history are unchanged.

## Interactions and media

Approvals bind Thread/Turn/callId, Host generation, effective argument digest and permissions. allowOnce/deny are supported; effectivePermissions.rememberAllowed=true additionally permits allowSession/allowProject without expanding Runtime Scopes. Questions allow 8 questions/8 options each, 4096-byte answers and 256 historical interactions. Waiting holds no model permit; Stop wins, and late/cross-Turn responses fail.

`permissions/read {threadId}` returns configuration (mode/allow/ask/deny), source, sandbox, workspace, session/project grants and projectFile. `permissions/forget {threadId,project}` clears session or project memory and requires an idle target Thread. Project approval requires manage without a threadIds restriction. See [permission configuration](../guides/configuration.en.md#permissions) for memory and rule precedence. Old snapshots without permissionGrants read as empty. thread/start/resume add permissionMode; full-access Runtime projects as dangerFullAccess.

POST `/areal/blobs?threadId=...` uploads raw bytes with Content-Type matching signatures. Tool uploads also supply callId/hostGeneration and require tools permission. Limits are 16 MiB/file, 128 registered uploads/64 MiB per Thread; no global cumulative Blob quota. Supported types are PNG/JPEG/GIF/WebP, WAV/MP3, PDF and UTF-8 text. GET requires authentication, threadId and reference ownership; a digest is not an access token.

contentItems preserve inputText/arealMedia order and deliver actual bytes to models. Authenticated RPC rejects host localImage/localAudio paths; use uploaded areal://blob URIs. Unsupported modalities fail explicitly.

The optional `DynamicToolCall.execution.fileBefore` is a `MediaRef` containing the complete bytes before a conditional write to a `workspace://repo/` file. After hooks and file-version aliases resolve, Core reads through Runtime in pages of at most 64 KiB. Core verifies each page's full-file SHA-256, size, contiguous offset, and the final content digest. The preimage contains at most 8 MiB with MIME `application/octet-stream`; empty files and binary bytes are valid. Core saves the Blob and its tool-record reference before submitting the original CAS write. Capture failures return `FILE_BEFORE_CAPTURE_FAILED` with `dispatch:"not_sent"` and the original cause. Cancellation during capture does not make the file write outcome unknown. UNKNOWN after submission still prohibits automatic replay.

Clients read the preimage through the existing Thread-authorized Blob GET. Archive, fork, and GC retain its direct history reference; fork validates the digest, byte count, and MIME. Only confirmed successful file writes can use this evidence to reconstruct a historical Diff, whose postimage must still match the successful receipt's digest and size. File creation needs no preimage. Older records without this field retain the verified full historical-read fallback. Missing evidence makes the historical version unavailable; current disk contents cannot substitute for history.

## Processes and retention

process/start defaults to lifetime=turn. Thread lifetime needs Profile allowThreadProcesses; writable services also need deployment allow-concurrent-writes. Input is attributed to authenticated identity. Output cursors and cleanup reuse Runtime facts. PTY resize uses actual ioctl; pipe EOF closes the FD, canonical PTY uses VEOF, and raw mode is unsupported.

The GUI terminal uses the account's executable login shell, with `SHELL` as a fallback and `/bin/sh` as the final fallback. The desktop adapter submits concrete argv for an interactive login session and supplies `SHELL`, `USER`, `LOGNAME` and `TERM=xterm-256color` through literal `/usr/bin/env` arguments. Login and interactive startup files establish the user's toolchain environment. Runtime retains its existing environment filtering and permissions. Recovery reads the original managed argv. A running terminal hides routine cleanup diagnostics; exited or uncertain processes retain their exit and cleanup facts.

The model-facing `development_service_inspect` lists only the current Thread's managed records, or returns one record with current Runtime state and at most 16 KiB of output. `development_service_start` submits a thread-lifetime process through the same durable process/start owner with a request identity derived from the trusted Core Thread, Turn and tool call IDs. Core approval, Profile permission and Runtime write-serialization checks still apply. An unknown start is inspected through the original record and is never automatically replayed. These tools do not provide a second process executor or infer a listening port.

Old-epoch handles return STALE_HANDLE without process restoration. Unconfirmed Thread process cleanup, active groups, and compaction prevent restartSafe. Historical tool or hook UNKNOWN alone does not prevent stopping the service; it still requires inspection before continuing its Thread. Archiving requires idle, settled queues/resources and releases hot history while retaining disk snapshots and deduplication keys. GC after drain scans hot/cold references and cannot collect referenced Blobs.

Events use areal/ prefixes, including thread/configured/archived, plan/updated, queue/updated, goal/updated/cleared, interaction/requested/resolved, process/updated and server/draining. Their revisions are not output cursors. Unknown model windows/usage remain null or absent rather than guessed. See [direct protocol examples](../examples/desktop-api.en.md).

features.goals=true advertises Goal support without a separate configuration toggle. Goal events follow the same authorization and atomic subscription boundaries. drain closes automatic continuation admission and pauses Goals; archiving and explicit compaction require stopping the Goal and awaiting resource settlement.

Local service discovery, window-independent lifecycle and Desktop Main integration use the [local service contract](local-service.en.md). `server/status` and `server/drain` additionally return `activeGoals` (Thread IDs) and `pendingQueueItems` (pending/running queue count). These are additive response fields; restartSafe still describes execution cleanup rather than absence of scheduled work.

Shared services expose `server/status.configuration` as `{modelRevision,applied,appliedRevision,applySequence,currentFileRevision,credentialStates,pendingApply,restartRequired,error}`; other deployments return null. `applied={revision,sequence}` identifies the file revision confirmed by Core. GUI model settings use the explicit hot apply interface above. Missing environment credentials during ordinary CLI model reload may report both `restartRequired=true` and `error`, indicating that a local client with valid credentials must perform a safe restart; other reload errors do not trigger automatic restart. `areal/server/configurationChanged` publishes `{threadId,configuration}` to subscribed threads. `server/drain` also accepts `strategy="ifIdle"`: check idle state and close admission under one gate; busy rejection keeps work running. See [configuration reload](../guides/configuration.en.md).

`server/status` and `server/drain` also return `lifecycle={version:1,admission:"open"|"draining"|"closed",ifIdle:{allowed,reasons},settled:{allowed,reasons},executionOutcomes:{uninspectedUnknown}}`. The outcome summary is an additive version 1 field. Its count covers historical tool calls or hook invocations requiring inspection, independently of physical resource settlement. `unresolvedTools` retains the original inspection entries. `restartSafe` equals `settled.allowed`.

`reasons` contains `{code,count}` entries with codes `activeTurn`, `resource`, `compaction`, `workgroup`, `activeGoal`, `queuedMessage`, or `activeTask`. Core shares observation policy with the operation check under its admission lock; observation does not authorize stopping. `ifIdle` requires no work and settled execution; `settled` is the execution/resource postcondition for cancel. Cancel retains paused Queue input without requiring zero pending messages again. Historical uninspected outcomes remain in the journal and keep the original Thread's continuation gate closed, but do not block service exit. Hook task scope uncertainty, unavailable Runtime observation, live Runtime processes, and unconfirmed cleanup remain resource barriers. A timeout can return draining, and RPC success does not prove process exit. Unknown versions, reasons, or missing permission fields cannot imply permission.

### Desktop adapter lifecycle

This GUI adapter protocol is separate from `areal.core.v1`. Authenticated snapshots advertise `service.lifecycle={version:2,desktopGeneration,capabilities:{request,read,reconcile,kinds},activeRequestId}` with stopDesktop, updateDesktop, stopProject, updateProject and interruptTurn.

`lifecycleRequest` carries `{protocol,requestId,kind,mode,expectedDesktopGeneration,expectedTargets,threadId?,turnId?}`. Mode is ifIdle or cancel; each target binds projectId/serviceId/generation. interruptTurn requires the original threadId/turnId. `lifecycleRead` and `lifecycleReconcile` accept protocol/requestId; reconciliation only reads the original Host or Turn, never ensure, drain or cancel.

Before effects, the Desktop owner saves a durable receipt with per-target Host request IDs and states. Overall phase is acceptedPending, blocked, partial, admissionUnconfirmed, settlementIncomplete or completed. When Desktop targets settle it records only desktopExit=requested; Main verifies original Desktop exit before displaying completion. Main durably saves request references before writes without becoming another execution authority. Lost responses and generation changes read original receipts; completed targets are not repeated. Uncertain targets restrict their projects while other projects remain usable.

Ordinary startup only attaches. GUI Main serviceLifecycle accepts only `{operation:update|stop|check}`; check does not change execution. Explicit update settles original targets and confirms Desktop exit before launching a replacement, retaining references on failure. Older adapters without these capabilities remain observable, without write probes or cross-layer cancellation fallback.

## Task Mode integration

The GUI read-only `tasks` command accepts `operation: list | inbox`, optional `projectId`, `limit` (1 to 1024), a UUID `requestId`, and a nonnegative integer `viewEpoch`. Omitting `projectId` still aggregates all saved owners. A scoped response echoes its identity and an `owners` outcome. A GUI receiving an older response without that identity requires a safe backend update rather than interpreting global rows as one owner's result. Each owner has a five-second deadline covering startup and every page. The deadline ends only the catalog read. Existing lifecycle code retains startup ownership. Unfinished reads are shared across retries. Expired work cannot fetch later pages or publish projections, and failures retain the previous complete rows. Each page checks a fixed client and connection generation. Repeated cursors fail the read. `[operation]` logs contain requestId, viewEpoch, projectId, stage, duration, page and row counts, and terminal outcome. Renderer `[task-catalog]` logs record receipt, commit, or abandonment without task content or credentials. A taskWatch receipt independently gates task management.

`task/create/list/read/pause/resume/cancel/subscribe/unsubscribe`, `channel/read/reply` and `inbox/list` form task control and communication APIs independent of Threads; see the [Task contract](tasks.en.md). task/updated carries a Task projection and channelSequence; clients retrieve Channel messages through pagination. server/status and drain report activeTasks for work that needs settling: scheduled tasks count only Runs that are queued, running, waiting for input or waiting for agents, including live Runs whose future schedule has been paused. An idle schedule awaiting its next trigger permits safe restart and retains its timing, enabled state and history. GUI/TUI/WebUI can share this Inbox; existing conversation interaction panels still handle synchronous questions and approvals.

Optional `parameters.contextWindowTokens` (1–2000000) declares model capacity and is retained in model defaults and Thread overrides. `areal/model/list.contextWindowTokens` remains null when undeclared; `effectiveContextWindowTokens` includes the global fallback. Context inspection adds budget fields windowTokens, outputReserveTokens, inputLimitTokens, targetTokens and windowSource (model/fallback). If model configuration or credentials are unavailable, context inspection still works and returns budget=null. This metadata controls local preflight; it does not change the provider model capacity.

## Turn Fork

`areal/capabilities` advertises `conversationDerivationV1` by default with `preview:false` and all six derivation methods. Fork supports `before` and `after` anchors at persisted Turns in a main conversation or Fork, with `sharedCurrent` workspace mode. Creation, listing, recovery, history and evidence reads retain identity, role and admission checks; clients enable actions from the current connection’s advertised methods and capabilities.

`areal/thread/fork` accepts `{requestId,sourceThreadId,anchor:{turnId,boundary:"before"|"after"},workspaceMode:"sharedCurrent",target?}`. Optional `target` selects an ordinary configuration with `agentProfile?`, `model?`, and `parameters?`; `{}` selects the deployment default, while omission freezes the configuration at the final inherited Turn. `before` excludes the anchor Turn; `after` requires a terminal anchor. Tools, hooks and plugin operations in the prefix must be settled; UNKNOWN requires source inspection. Core reads the anchor prefix from a committed source record and fixed cold segments; when the source is itself a Fork, its inherited snapshot is flattened first. Core persists a target-owned snapshot, per-Turn source IDs and creation receipt, then publishes an idle independent Thread and Session. Its local `turns` start empty; source Goals, queues, approvals and execution hosts are not inherited. Creation starts no model or tool and does not change workspace files. Creation and same-key replay return a Thread summary with empty `turns`; read or observe the target to recover its current history. The same business key and parameters return the same target; conflicting parameters return `REQUEST_CONFLICT` in `error.data.reason`. `conversation.kind=fork`, `origin` and `historySeed` describe content provenance, not a `parentThreadId` delegation.

`areal/conversation/history {threadId,view:"inherited"|"reference",cursor?,maxBytes?}` authorizes against the target and pages Fork inherited history or a Side reference snapshot, with a 64 KiB default and 256 KiB maximum covering the serialized result. Cursors bind the target, snapshot, view and position; reuse across targets or views is rejected. An absent history layer returns empty data, snapshotId=null and complete=true. Oversized items are split at UTF-8 boundaries: fragment.text contains consecutive portions of the complete entry JSON with offsetUtf8, nextOffsetUtf8 and totalBytes. Clients concatenate and parse these fragments without creating execution events. Each complete entry includes `turn` presentation metadata for the original status, error, timing and Goal, without items. The GUI groups entries into Turns and renders them in the main message timeline without an inherited-history disclosure. Fork and Turn menus appear with the copy action only after the response ends. `areal/context/read` and subsequent target model requests build logical history from the persisted snapshot and local Turns without reading the live source. The snapshot limit is the smaller of the configured history limit and 64 MiB. Tool batches, settled results, media and raw-result references remain historical facts; they are not registered as new target executions or usage. The target may read only Blobs referenced by its snapshot. The target model must support inherited modalities and native Provider context format; creation otherwise returns `MODEL_MODALITY_INCOMPATIBLE` or `MODEL_CONTEXT_INCOMPATIBLE`. Automated Workflow Profiles return `PROFILE_NOT_SUPPORTED`. Old records without `conversation` remain ordinary main conversations; unknown kinds or unsupported versions fail recovery.

## Side Chat

The `areal/side/start` request is `{requestId,sourceThreadId,anchor?,selection?,workspaceAccess:"none"|"readOnly",input:[{type:"text",text}]}`. The anchor may be `latestCommitted` or `{kind:"turn",turnId,boundary:"before"|"after"}`; omission selects the last committed Turn when the first question is accepted. `selection` may be `{kind:"itemRange",turnId,itemId,startUtf8,endUtf8,textSha256}`: Core verifies the UTF-8 byte range and SHA-256 digest against one text Item in the frozen prefix, so repeated text remains position-specific. An invalid boundary, range or digest returns `STALE_SELECTION` without submitting the first question. For uncommitted or unmappable text, use `{kind:"userQuote",text,claimedTurnId?,claimedItemId?}`; it persists as an unverified user quote, and the claimed IDs do not prove provenance. `turn/after` accepts completed, failed and interrupted Turns, and rejects an active Turn with `TURN_NOT_TERMINAL`. Opening an empty pane creates no Thread. The first question commits an independent Session, immutable reference snapshot, first Turn and request receipt together, then starts the model. Repeating the same key returns the same target and original first Turn even after archive, cold-history eviction or restart, without executing or unarchiving. Creation and same-key replay return summaries with `thread.turns=[]` and `turn.items=[]`, retaining target and first-Turn identity, status and configuration; recover full history through the target read/observe routes. After a lost response, query `areal/request/read {requestId}` instead of retrying under another key. A committed but unfinished Turn is marked interrupted on restart and is not resubmitted.

Side's `conversation.kind=side` and `policy.kind=sideReadOnlyV1` are durable roles; `none` permits only the fixed Core `side_context_read` tool; `readOnly` intersects the source's current tool allowlist at creation, identity authorization, deployment permissions and the trusted native Runtime `fs_read`, `fs_list`, `fs_stat` and `search_files` tools against current workspace files. Historical anchor configuration cannot widen this authority; the frozen tool subset survives model configuration, archive and restart. `areal/capabilities.features.conversationDerivationV1.sideWorkspaceAccess` advertises `readOnly` only when the native path sandbox, file helper and search capability are verified and no command hook is configured. Otherwise creation returns `WORKSPACE_READ_UNAVAILABLE`, and users may explicitly select `none`. The Side Runtime scope has the workspace read root only when its frozen subset contains file tools; otherwise read roots are also empty. Write roots are empty and network access is denied; commands, MCP, plugins, dynamic tools, Goals, automated Workflows and delegation cannot execute. File reads report `source:"currentWorkspace"`, the observed SHA-256 and range; another read of the same path in the Turn reports `changedSincePreviousPage:true` when the SHA differs. Directory and search results are also current-workspace observations, without an atomic cross-page snapshot. Historical instructions and tool output are reference data. Model context includes bounded recent excerpts, evidence references and an omission count; follow-ups use the original snapshot. `areal/side/context/read {threadId,evidenceRef?,cursor?,maxBytes?}` pages through frozen evidence under target authorization, with a default budget of 8192 bytes and a maximum of 16 KiB. `evidenceRef` and `cursor` are mutually exclusive. The GUI labels evidence with its snapshot and verification status and does not claim it is current when the source advances or its current state is unknown. Legacy execution routes cannot change the Side role or widen access, and the default `thread/list` task list excludes Side. `turn/start` and `areal/turn/start` accept text follow-ups only; `turn/interrupt` stops only the current Side Turn. Closing the GUI pane sends no interrupt.

GUI selections from a completed Turn default to that Turn's `after` anchor; streaming user quotes use the latest persisted observation at first-question acceptance. If rich rendered text cannot map directly to canonical text, the GUI marks it as an unverified `userQuote` even when the reply is complete. A selection over 16 KiB in original bytes, or one that cannot fit the initial context after escaping, returns `SELECTION_TOO_LARGE`. The initial model package is limited to 32 KiB of serialized UTF-8; `maxBytes` for evidence pages includes the whole serialized result and rejects a budget too small for one page. Selecting from an existing Side opens a new draft and leaves its old snapshot intact.

The GUI can bring selected text or an explicitly chosen whole Side answer into an editable preview with the Side and source snapshot identified. Confirmation checks the captured service instance, project, source conversation, and Side owner, then appends to the latest local main draft with a local insertionId dedupe; existing attachments and model choice remain intact. If the source advances, the preview labels the older snapshot. If the source is archived or the target changes, the preview remains available for copying. This operation changes only the local draft: it neither sends, queues, steers, nor unarchives a conversation.

`areal/conversation/list {view?,sourceThreadId?,includeArchived?,limit?,cursor?}` classifies conversations as `main` (default), `side`, or `all`. Archived conversations are excluded by default; `limit` is 1–100 (default 30). `main` includes ordinary main conversations and Forks but excludes delegated Workers and Side. `sourceThreadId` applies only to `side`/`all`. Results use stable `createdAt,id` ordering, and cursors are bound to identity and filters; cross-filter reuse is rejected. The old `thread/list` contract remains unchanged. The GUI uses the new list for main navigation, explicitly including archives for its archive view, and pages related discussions by source. Manual refresh discovers Side conversations created by other clients.

On authenticated connections, observe permission alone cannot create a Side. A principal with `threadIds` cannot create a derived conversation even with source read and interact permissions: the response carries `error.data.reason=SCOPED_PRINCIPAL_UNSUPPORTED` and does not extend visibility. List, read, evidence, Blob and request-key receipt access authorize the target Thread independently; seeing a target does not grant access to its source or another Side. Request media retained in a Side snapshot with that Side's `threadId`; guessing a digest does not authorize another conversation's Blob. While idle, a Side accepts `areal/thread/configure` only for `model` or `parameters` with `expectedRevision`, preserving its read-only role and tool scope; options, Profiles, Skills and resetModel are rejected. `areal/tool/acknowledge` can save an explicit inspection note on Side-owned UNKNOWN tool records while preserving their UNKNOWN outcome and preventing replay; it cannot acknowledge source or reference-snapshot tools. Other legacy execution routes enforce the durable Side role against writes or privilege changes. The GUI Core client preserves `data.reason` and `data.requestId` from errors.

An idle Side can be durably archived with `areal/thread/archive {threadId}`; an active turn rejects archive. `areal/conversation/unarchive {requestId,threadId}` idempotently restores an archived Side and its full history without starting a model turn. Replaying the original Side creation key returns its original first Turn from durable history, including after restart, without executing or restoring it. Reading or subscribing to an archived Side does not restore it, and sending while archived remains blocked. Stopping or archiving the source does not stop or delete the Side; closing the related-discussion pane only hides it. Core restores sent content after GUI or Core restart. Unsent drafts have no cross-process persistence guarantee.
First questions and follow-ups share active Side capacity: two per source and eight per deployment by default. Exhaustion returns `SIDE_SOURCE_CAPACITY_REACHED` or `SIDE_DEPLOYMENT_CAPACITY_REACHED`. Each Side Turn defaults to at most eight model rounds, 16 tool calls and 300 seconds; global limits can tighten these. Side skips automatic and manual model compaction to avoid requests outside this allowance, and reports context overflow. When a model permit is unavailable, `areal/side/capacity` emits `waiting`/`available`; `thread/read` and subscription snapshots from `areal/thread/observe` / `thread/resume` project the current state as `desktop.sideCapacityStatus` for an active Side. Snapshots clear this waiting state after the Side stops. Stopping affects that Side only. Side requests count toward their own Session and real deployment usage, without inheriting the source Goal budget.

## Side model and cleanup recovery

`areal/side/start` without `model` or `resetModel` inherits the anchor model. `resetModel: true` explicitly selects the deployment default; `model` selects an explicit model. Combining them is invalid. Existing clients retain inheritance semantics; an older Core must reject unsupported resetModel instead of silently inheriting. First and subsequent questions share the persisted configuration.

Side restore has idle/loading/ready/error states per owner and connection generation. A definite error waits for explicit retry; a new target or connection can read again. Old results cannot update new targets. Unknown submissions only reconcile their original receipts and never replay the first question.

MCP cleanup failure remains cleanupFailed with persistent cleanupUnconfirmed. Repeating disconnect without a live connection is no cleanup evidence and cannot clear the state or start another host. Directory rollback also propagates unconfirmed cleanup. Restart does not clear the marker. There is currently no remote RPC to claim successful cleanup; an operator must independently verify the task-owned host exit before repairing the record through maintenance. This state alone does not prove a process leak.

## Desktop background command compatibility

The authenticated `areal.desktop-service.v1` snapshot adds `service.commandContract: "areal.desktop-commands.v1"`.
