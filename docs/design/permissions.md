# 权限架构设计提案

状态：待评审，尚未实施。代码基线：`a78bce5`，核对日期：2026-10-13。当前行为仍以[权限配置](../guides/configuration.md#permissions)和[Runtime 契约](../api/runtime.md)为准；架构归属见[分层与目录](architecture.md)。

**建议让 Agent 默认在受限环境内自主完成任务，需要新增能力或命中明确审批规则时再请求确认。** 保留现有审批、授权记忆和 Runtime Scope；重点补齐安全的自动执行预设，以及把审批结果转成实际执行权限的 Core 授权代理。

用户应能理解三个问题：**现在能访问什么、为什么需要询问、批准后究竟多了什么权限。** 不要求用户理解 Scope 树，也不要求模型准确预测任意脚本的副作用。

## 一套决策，两个问题

每次操作都必须分别回答：

1. **是否允许发起这次操作？** 工具规则、命令规则、用户审批回答这个问题。
2. **执行时最多能访问什么？** 文件、网络和外部服务权限回答这个问题，由实际执行方落实。

例如 `npm run build` 命中允许规则，可以省去一次确认，但仍只能访问本次 Scope 允许的资源。即使项目后来修改了 build script，也不能因此获得工作区外写入或网络访问。沙箱内普通文件仍可能被错误修改，沙箱不替代代码审查和结果验收。

这里需要明确区分三个概念：

| 概念 | 含义 | 例子 |
|---|---|---|
| 硬性上限 | 普通审批和授权记忆都不能突破的限制 | 部署禁网、Profile 强制只读、父任务的工具禁用、可信控制数据保护 |
| 基础权限 | 当前任务无需额外申请即可使用的范围 | 读写工作区普通文件、使用任务 scratch、默认不联网 |
| 附加授权 | 在硬性上限以内，明确批准的额外能力 | 本次操作可写指定导出目录，或临时联网 |

**本次有效权限 =（基础权限 ∪ 本次附加授权）∩ 部署上限 ∩ Profile 与父任务强制限制。** 显式拒绝继续优先；“允许启动”也不能绕过工具禁用。

“默认不联网”可以允许申请联网；“部署禁止联网”应直接拒绝，并说明用户在当前会话中无法覆盖。这一区分也适用于路径、只读任务和子 Agent。附加授权不能自动传给子 Agent，子任务只能取得明确委派且不超过父任务约束的能力。

## 各层继续负责什么

| 所有者 | 目标职责 |
|---|---|
| 可信 launcher / 部署 | 确定硬性上限、可信程序和控制数据位置、可用的隔离机制。 |
| Core 权限决策 | 汇总规则、任务限制和有效授权，返回允许、询问或拒绝，并解释原因。仍在现有 Core 内，不新增独立权限服务。 |
| Core 授权代理（Permission Broker） | 将获批能力绑定到具体操作，建立受限执行 Scope，管理有效期、取消与回收。Agent 和工具 Host 不能拿到宽权限根的任意签发能力。 |
| 现有 Interaction / Store | 展示与记录审批，校验回答身份，保存授权记忆和操作结果。复用现有历史，不另建审批系统。 |
| Runtime / 工具 Host | Runtime 强制执行本地文件与进程边界；外部 Host 对自己承诺的能力实施约束。不能兑现的限制必须明确报为不支持。 |
| GUI / CLI / Remote | 提交意图、展示 Core 返回的有效权限及审批。前端标签或远程项目访问权都不能扩大执行权限。 |

统一的是决策语义和授权依据。MCP 的远程删除、Browser 的页面操作、本地命令的文件访问仍由各自执行边界负责，不必先建设一个覆盖所有未来工具的庞大 Capability 框架。

## 一次扩权应该怎样发生

以文件工具能够确定目标的“生成报告并保存到工作区外指定目录”为例：

1. Agent 在基础 Scope 内读取项目、生成报告；这些操作不打断用户。
2. 保存到额外目录需要权限。Core 根据工具的最终参数和目标，先排除硬性禁止，再提出“本次写入该目录”的申请。Hook 修改过参数时，审批应绑定修改后的操作。
3. 用户看到具体操作、目标、增加的能力和授权期限。批准只代表允许这项增量，不表示关闭沙箱或提高整个会话的权限。
4. Core 重新确认操作仍属于活动任务、参数和策略没有变化，签发包含必要基础能力及这项增量的 Operation Scope。Runtime 校验并执行；其他路径仍不可写，网络仍关闭。
5. 操作及其受管资源结束后关闭 Scope，记录实际边界、结果与清理状态。后续操作恢复使用基础权限。

当前子 Scope 只能收窄父 Scope，这个约束应保留。需要扩权时，由可信 Core 从部署允许的权限上限中另建受限操作 Scope，同时重新施加原任务限制。**这个 Scope 即使不是基础 Scope 的子节点，也必须继续归原 Turn 的取消、总预算、并发限额和清理机制管理。** 不能通过更换父 Scope 绕过任务约束。

当前 native 根 Scope 的资源权限只有工作区与 scratch，新建其子 Scope 不能取得其他目录。额外路径授权需要把“部署可授权哪些路径”与“是否裸机执行”解耦；不是多加一个弹窗就能完成。

授权必须绑定实际操作、目标范围、执行方和有效期，并在执行前重验。任意脚本需要哪些能力不能总被预先推断，应依据明确请求或可信拒绝诊断提出扩权；不能只信模型填写的“只读”或“安全”描述。

### 审批、重试和撤销的边界

现有精确调用记忆可以继续回答“相同调用是否需要再次询问”；新的能力授权回答“执行能访问哪些资源”。二者不能互相替代，旧的命令审批记录也不能自动升级成全目录或联网授权。

首版附加授权只支持一次操作，生命周期包含该操作管理的进程，而非仅到工具返回为止。后续会话/项目复用应保存有明确范围的授权规则，每次使用重新核验并签发新 Scope；不保存长期存活的宽权限 Scope。现有显式 ask、强制审批不能被记忆跳过；无法核验连接代际的 MCP 继续仅允许单次回答。

取消、审批过期或身份变化后，未提交操作不得启动。已经提交的操作按现有取消路径处理，并等待清理结果；清理失败或执行结果未知时，保留 UNKNOWN，不宣称副作用已撤回。权限不足也不意味着命令完全没有执行：复合命令可能先产生了部分结果，不能批准后直接自动重跑整条命令。重启不重放未知操作，也不恢复一次性能力。

“清除记忆”保持当前含义：停止后续复用，现阶段要求目标 Thread 空闲。“停止正在使用的授权操作”则必须走取消与清理；远程服务已受理的副作用不能保证撤销。无人可审批时，返回明确的权限需求，不默认放行。

## 自动执行预设应提供什么

Safe Auto 是设计阶段对受限自动执行预设的称呼。产品继续把工作方式和实际权限分开展示：Plan 保留独立入口；审批选项建议用“执行前询问 / 自动执行”，避免“帮我审批”暗示已有 Reviewer。

| 工作方式 | 目标行为 |
|---|---|
| 计划 | 保留现有工作区只读、任务 scratch 可写、Runtime 网络关闭及外部 Host 限制。强制只读 Profile 不能通过批准计划解除。 |
| 执行前询问 | 使用受限基础权限；已知读取免确认，修改、命令和外部操作继续按现有 Ask 语义询问。批准后仍受相同资源边界限制。 |
| 自动执行 | 相同的受限基础权限；普通编辑和本地命令自动运行，显式要求审批的动作与能力扩展才询问。 |

Full Access 是另一维度的高级部署选项；必须明确展示扩大后的实际访问范围，仍服从显式拒绝、Profile 和任务限制。

Safe Auto 的基础权限包括工作区普通文件、任务专用 scratch，以及运行工具所需的只读系统/工具链路径。默认关闭命令网络，不开放整个 HOME，不把模型凭据注入命令。工作区里原本存在的敏感内容不会被自动识别；更细的文件读取拒绝规则属于后续能力。

受保护内容分两类：可信 Core/Runtime 程序、授权记录和权限配置属于不可由普通工具修改的控制面；仓库 `.git`、`.agents`、`.codex` 等元数据默认限制写入。正常 Git 工作仍需可用：明确授予必要的元数据写入，同时保留控制配置与 hooks 等保护，不因允许 `git commit` 就放开整个仓库管理目录。现有只读目录保护没有完整的细粒度例外语义，这部分需要扩展，而不是直接套一个目录黑名单。

保护必须同时覆盖文件工具和任意脚本，按真实路径处理链接与重命名，不能只检查字符串前缀。项目内文件不能自我批准、修改硬性上限或写授权存储；项目声明只能在可信用户确认的范围内生效。

Core 应返回操作的真实执行边界、权限来源、额外授权和拒绝原因。现有 `permission_read` 与 Runtime 能力投影可复用，但当前部署级 `sandbox` 字段不能代表每个 Turn 或工具。GUI 应能显示“工作区可写 · 网络关闭 · 外部工具另行授权”，并在详情中解释。

## 命令、网络和外部工具的明确取舍

**命令规则负责减少不必要的询问，不授予额外资源。** 首版支持参数前缀的允许、询问、禁止，拒绝优先。`git status && git push` 必须分别判断各段；命令替换、重定向、解释器包装等无法可靠分析的部分不能从无害前缀继承豁免。Auto 下普通未匹配命令可在沙箱内运行；无法可靠分析的复合表达式保守询问。规则也不能覆盖现有强制审批。

这套规则不承诺识别任意脚本内部的删除或发布。允许 Python 不代表能证明 Python 程序安全；若要求“任何渠道的发布都必须审批”，还需要目标服务或网络执行层的约束。

**首版网络能力如实保持开关粒度。** 若部署允许，可批准某次操作临时联网，但界面必须说明这是该进程及其子进程的网络访问，目标不限于申请理由中的某个域名，且可能包括内网。此授权不改变文件边界。需要“仅访问包仓库”的产品承诺时，必须先交付实际拦截直连、域名解析和私有地址访问的网络出口控制；不能把一张域名列表当作执行保障。

**外部 Host 需要独立建立信任。** Core、Plugin Node Host、stdio MCP 不在 Runtime 沙箱中；Browser 普通页面加载也使用自己的网络边界。Safe Auto 的文件与网络承诺只覆盖受控执行路径，不代表模型请求、MCP、Browser 自动共享同一限制。复用现有 Browser 操作绑定和审批；未建立信任或无法兑现所需限制的 Host，拒绝自动执行，不能因其自报只读而放行。经可信用户启用的 Host 按工具风险审批，并明确告知宿主权限；需要不可信插件隔离时再建设实际 Host 沙箱。

## 先交付什么，再扩展什么

| 阶段 | 交付结果 | 进入下一阶段的条件 |
|---|---|---|
| 第一阶段：可选 Safe Auto 闭环 | 受限基础权限、保护路径、命令规则、一次性目录/联网扩权、Core 权限解释；复用审批与 Scope 生命周期。 | 正常开发可完成，越界副作用被实际阻止，取消与未知结果不导致重放；外部 Host 的覆盖范围明确。 |
| 第二阶段：扩大默认覆盖 | 先向新安装默认启用；完善按目标网络限制、细粒度读取拒绝、能力授权复用及外部工具风险策略。 | 每项界面承诺都有对应执行约束；旧部署显式迁移，强制策略不能被弱化。 |
| 后续按需求投入 | 自动审批审查、组织策略管理界面、规则建议、更多平台隔离。 | 确定性权限边界已经稳定，再优化审批成本。 |

第一阶段以“工作区修改 → 运行本地测试 → 申请写入一个额外目录 → 确认其他目录仍被拒绝 → 结束并回收”为完整验收路径。联网扩权使用同样的绑定与生命周期，并独立验证。这样先验证授权是否真正限制执行，而不被域名代理或自动审查的复杂性拖住。

改变产品默认前，必须验证 Git、Node、Python、Cargo、常用测试工具及缓存/临时目录。沙箱不可用或工具链路径未授权时，明确失败并说明缺少什么；沿用当前不静默降级的行为。可信程序、控制数据和授权存储必须位于 Agent 可写范围之外。切换部署涉及共享服务兼容性与重启，不能在已有任务运行中仅改一个 GUI 标签；已有 Full Access 部署保留真实标识并显式迁移。

验收复用[权限 smoke](../../scripts/permission-modes-smoke.mjs)和 Runtime 现有检查，补充真实副作用断言：普通源码写入成功；工作区外及保护路径写入失败；组合命令不能借前段豁免后段；一次授权不能复用或扩大；取消后的审批不能启动操作；子 Agent 不能越过父级强制限制；受信任外部 Host 不被误报为沙箱内执行。还要验证失败不静默切换 Full Access，已提交但结果未知的操作不被自动重试。

安全验收看真实文件、网络与进程结果；可用性验收看典型任务完成率、审批次数和额外耗时。文档核对不是这些运行时场景已经通过的证据。

本提案建议优先确定三项产品选择：受限自动执行作为新安装的目标默认；命令允许规则始终保留沙箱；扩权默认只绑定一次操作。其代价是先补工具链兼容、可信控制面保护和授权生命周期，收益是普通开发少打断，越界授权可解释且可执行约束。
