# 基准测试方法

运行命令见[基准指南](README.md)，改进目标、通用性与默认策略门禁见[Agent 改进方法](../development/agent-improvement.md)。真实任务收益、确定性机制回归、并发原语容量分别报告，不互相替代。

1. 运行前固定源码、题目、镜像、模型、参数、资源上限、重复次数和选择规则；同题同重复配对，顺序随机交错。
2. 以可信最终验收判正确，不用 Agent 自报、退出码 0 或局部编译代替。原始题与派生子任务明确区分；记录空测试、跳过和评分异常。
3. 保留全部计划尝试，包括失败、中止、超时、补跑和淘汰题。答案正确、正常完成与有效评分是独立状态。
4. 报告全部尝试耗时/已知 token，再对双方都正常完成且正确的同题计算比值。选择第一条合格样本，不挑最快；展示配对数量，缺少样本不比较。
5. 未报告 usage 保持未知，失败部分用量是下界。缓存输入已包含在 input 中，不重复累加；CLI 累计与公共观察器覆盖分别标注。
6. 单个用户 Turn、模型请求数、工具调用数和进程数量分别计量。模型许可占用包含网络/流等待，不代表 GPU 利用率；工具成功率不代表解题正确率。
7. 测量日志可能含提示/源码/服务信息，发布前脱敏并确认再分发范围。保留来源摘要，但不把仅有摘要称为完整可复现证据。

提高 Worker 上限不保证收益。与单 Agent、固定并发对比时，保持相同输入、授权和最终检查，并同时报告验收/修复成本。小样本、事后选题、不同版本或模拟环境只能作限定条件下的描述，不推出一般排名。

开发、确认与回归材料分开，按来源组隔离而非仅按题号随机拆分；看过或用于修复的题不再是未见确认题。同源变体和改名只验证稳健性。长期软件工程、浏览器、文档、数据各占 25%，同时报告领域结果与来源覆盖；不完整领域不能凑成整体分数。

每轮先固定机制假设、干预变量、最小收益、退化界限、确认样本和停止规则。将提示词、工具、协议桥、适配器、自动续轮、默认配置与全部根预算纳入冻结身份；题族预算或额外策略必须显式披露、单独比较，不能隐藏在接入层。联合修改只产生组合效果证据。

晋级默认行为须有相符的开发对照和未参与调优的来源隔离确认。负向结果保留并停止晋级，不能继续用同题扫阈值直至通过。正确性修复可凭不变量与必要回归合入，但不得因此宣称通用提分或降本；尚未验证的候选和效果明确标注。

## 重复次数、覆盖面与证据规模

正式策略比较默认对每道题、每个 Harness 独立运行至少 5 次，每次新建状态、使用相同单次根预算；冻结并记录重复编号、调度种子、实际模型参数和完整尝试。配对相同题与重复编号，随机交错执行，不能将上次答案、工作区或失败恢复泄漏给下一次。5 次用于观察随机波动，不代表 5 个独立题或足够统计功效；报告单次成功率分布，不能以五次取最好或 pass@5 冒充单次能力。

| 阶段 | 运行前的最低计划 | 允许的结论 |
|---|---|---|
| 链路 smoke / 契约回归 | 可显式 `--repeat 1`，使用模型桩或少量题验证输入、执行和评分 | 只证明所检查的链路或不变量 |
| 策略开发对照 | 至少 12 道不同任务，来自至少 3 个独立来源组；每题每方至少 5 次，即每方至少 60 次完整尝试 | 诊断适用范围与反例；限于实际覆盖的领域，不推广默认值 |
| 全局默认晋级 / 整体排名确认 | 冻结方案后，至少 48 道未参与调优的任务，每方每题至少 5 次，即每方至少 240 次完整尝试；覆盖至少 3 套独立 Benchmark，软件工程、浏览器、文档、数据各至少 12 题、各至少 2 个独立来源组，与开发材料按来源隔离 | 仅在预先定义的质量、效率、退化与不确定性门禁同时满足时支持推广；固定数量本身不证明成功 |

这是最低工作量，不是充分性证明，也不要求每个确定性修复启动真实模型评测。限域策略须预先声明领域，并在该范围使用同等来源隔离、至少 12 题 × 5 次的确认；不能据此推广到全局。资源不够或暂缺独立来源时保留小批次结果为探索证据，策略继续显式实验，不降低确认门槛。

Benchmark 名称、来源组、任务数和重复次数分别计数。一个代码仓库、应用、数据生成器或母题的改名/改数据/难度变体仍归同一来源组；不同套件共用母源时不能凑成独立 Benchmark。多跑同一道题只能增加重复数，不能补齐任务、来源或领域覆盖。现有 Docker `lite` / `pro` 不自动构成跨四领域的独立确认覆盖。

运行前提交评测计划，逐行列出阶段、Benchmark 及版本、来源组、领域、题目摘要、是否已见、每方重复数、根预算、模型身份、顺序种子、排除规则、主指标、最小有意义差异与停止规则。基于先导开发数据估计方差和所需规模；计划不足以分辨目标差异时，在确认开始前扩充任务与来源。确认中不得看见有利结果便提前停止；只有预先登记的序贯方案或资源/安全停止条件可以改变运行，保留计划与实际缺口。

报告领域及来源分层结果、全部计划尝试的成功/失败/UNKNOWN/待审、每题重复分布，以及配对质量差、耗时和 token 的区间估计（默认 95%）。按来源组进行配对聚类重采样，并保留组内题目与重复结构，报告方法、种子和独立组数；不能把同题重复当独立样本。来源太少、用量不完整或区间过宽时明确证据不足。排名优势要求质量差的区间支持预定最小收益；效率改善还须满足预定质量非劣与领域退化约束。不要按单次最好值或仅比较成功子集来证明整体优势；成功配对的效率只作条件指标。

`scripts/perf run`、`compare` 与交互入口默认 `--repeat 5`，子集仍由显式 `--task` / `--case` 选择。工具只执行所选任务，不自动补齐上述跨套件来源覆盖、运行来源隔离确认或判定默认晋级；计划与报告必须单独核查这些条件。最低次数与固定种子不能保证供应商返回完全相同的随机序列。

## 公共用量观察器

`tests/perf/runner/model_observer.py` 对每次 HTTP 尝试采集元数据，不抽样丢弃请求，也不改变请求体、缓存键或重试策略。服务端 `x-request-id`、响应 ID 和本地唯一观察 ID 用于定位；不保存凭据、提示或输出正文。

观察器按空行提交完整 SSE 事件，支持跨分块、LF/CRLF/CR 和多行数据，区分完整计量回执、部分用量与未知。EOF 尾部只有完整可解析的 JSON 才可恢复计量，并标记 `eof_receipt_recovered`；这不代表 SSE 事件已完整分帧或送达。矛盾响应身份或计数使该请求用量保持未知，不混加。完整的供应商用量回执即使来自失败或截断终态也计入消费；任务成败、流完整性和用量完整性分别记录。缓存计数缺失保持未知，不补零；`usage_field_coverage` 给出各字段覆盖数。旧记录没有回执来源标记时，保留原保守口径。

`usage_receipt_version=2` 的 `usage_requests` / `usage_coverage` 表示有完整供应商计量回执的尝试数及比例，不再要求任务成功。`usage_unknown_by_reason` 区分 HTTP 错误、上下游断开、缺终态、解析问题和关闭时仍在途的请求。不能将覆盖率改善直接解释成任务成功率或成本下降。

收到完整用量后立即更新内存快照，并向相邻的 `*.lifecycle.jsonl` 提交元数据检查点；HTTP 尚未 EOF 的已收回执也进入关闭快照，只计一次。元数据写入使用有界后台队列；磁盘失败、队列丢弃和关闭时未落盘数量经 `metadata_persistence` 显式暴露，不等待磁盘恢复、不影响转发。队列不是事务账本，不保证强杀或断电时零损失。

取消后立即沿原路径关闭上游，只解析已经接收的字节，不为补统计继续读取、延长生成、重试或查询其他 API。没有收到的服务端回执仍为 UNKNOWN。支持存储响应的供应商可另做授权后的离线对账，当前观察器不自动检索响应，也不将估算 token 当作真实用量。

机制回归：`python3 -m unittest discover -s tests/perf/tests -p 'test_model_observer.py' -v` 与 `python3 -m unittest discover -s tests/perf/tests -p 'test_usage_capture.py' -v`。本地 HTTP fixture 验证转发字节、取消、并发、磁盘故障和快照；不证明真实上游故障的缺失用量能够恢复。
