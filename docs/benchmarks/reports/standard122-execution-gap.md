# Standard122：三方 Agent 执行核心与失分机制

## 结论

这批结果支持的判断不是“AReaL 的整个 Agent loop 都比另外两者差”，而是：**执行协议的可靠结束、工具操作成功、自建检查通过，与用户要求的完整交付之间仍有明显缺口；能力准入、工具认知成本和失败恢复还存在可定位的损耗。**

优先处理顺序是：交付位置与验收覆盖 → 委派执行能力准入 → 协议失败的安全恢复 → 浏览器状态确认与上下文效率。不是先重写 Runtime、堆更多 Agent、加长全局提示，或默认扩大预算。

本报告把机械门禁适配与语义能力分开讨论：四个关键引用零分实际由开头的格式说明触发，不能统称为事实幻觉。本报告只做离线诊断，没有修改产品行为、题目、评分器，没有重新调用 Solver/Reward。结论来自完整平台矩阵、文档原生轨迹及定向补读的六份最终原生状态；不是对 1,066 次尝试的逐步穷尽审查。统计与制品指纹见[机器证据](standard122-gap-evidence.json)，方法约束见[Agent 改进方法](../../development/agent-improvement.md)。

### 量尺敏感性：格式说明也被当成真实引文

进一步读取实际 `deliverables.tar.gz`，四个触发点均在开头的**引用格式说明**：011 的 `RELEASE_NOTES.md:3`、012 的 `RUNBOOK.md:7`、014 的 `ADR.md:5`、015 的 `REPORT.md:3`。例如“引用统一写作 `[src:资料ID]`”和“带 `[src:…]` 引用的结论”。这不是发现四份正文都用假资料支持事实。

公开 `012/public/TASK.md:17` 本身用 `[src:资料ID]` 解释格式；本地对应制题源 `object-id-contract-r6/.../012-apispace-runbook/oracle/check.py:13,167–169` 则对**整个文件**执行引用 regex，与 registry 做差，包括反引号内的格式示例。它与观察到的错误一致，但本报告没有重建线上评分器来证明源码/运行制品逐字节同一。

因此，这四题首先证明**输出卫生/严格机械门禁适配**差异，包含格式示例与引用语义的契约边缘；不能把相应零分全解释成事实推理缺陷。尤其不能将 Qwen 对 DSH 的 5.012 个总分百分点直接当作等幅度的实际工作质量差距。保留原分，不为候选改隐藏断言；若要评价真实文档质量，应对三方匿名、独立语义复审，并另行审查门禁对元说明的处理。014 的 ownership 错和错误目录失交付仍是独立问题。

## 3. 配对执行轨迹揭示的机制

### 3.1 自建检查器与产物共享盲区

`N/areal/qwen/012-apispace-runbook.json` 的事件 30、32 是失败检查，后续修复了 excerpt 与引用集合；事件 48 的检查仍只覆盖选定 claim/excerpt，最终宣称自检通过。平台指出正文另处存在无效资料 ID。011、014、015 也出现“局部检查绿、全文门禁红”。

DSH 对应四题均通过自动门禁，Codex 只通过其中两题。可归纳的差异是**交付约束的覆盖与最终检查对象**，不是 DSH 有一个保证语义正确的神奇验收器。证据：`D/documents-metrics.json` 中对应 assessment，三方 N 中的检查命令与实际交付。

通用假设：模型同时写产物和选择检查范围，容易反复确认自己已经相信的部分。应把公开要求逐项关联到最终产物和检查证据，尤其检查整个文件集合；不是对任何任务强塞固定的来源 ID 检查或再加一轮空泛 review。

### 3.2 验证路径与交付路径不是同一个位置

`N/areal/qwen/bx-doc-controls.json` 事件 11 已观察到模板实际位于 `/envarena/workspace/inputs`；事件 19、31 却把产物写到 `/var/lib/ah-state-…/repo/output/completed.docx`。事件 31 的重新加载、内容控件及保留性检查成功，最终自报完成；assessment 报候选目录缺 `completed.docx`。原生回执也是 OK，15 次请求且未耗尽预算。

DSH/Codex 同题均为 1。此例说明：**验证了一个正确文件，不等于把它交到用户要求的位置**。Core 的 workspace URI、真实 cwd、私有状态根和 scratch 都可同时存在；模型拼出一个看似合理的 `repo` 不会自动映射成 workspace。改进边界是统一并显式呈现有效工作根、保持相对输出路径、核验最终交付集合；不是根据某个评测私有绝对路径写特例。

### 3.3 委派能力暴露了，但执行先决条件不成立

直接检查全部 44 份 AReaL 文档原生状态：

- Qwen：1 个父任务创建 2 个子任务，**2/2 失败**。
- Astra：22 个父任务创建 24 个子任务，**24/24 失败**。
- 全部 26 个失败子任务都保留了 `bwrap: setting up uid map: Operation not permitted`，随后以 UNKNOWN/执行失败结算。

同类失败也见于定向补读的 PTY、WAL、浏览器任务。它不是“模型不愿协作”，而是**外层评测隔离中，子执行所需的嵌套原生沙箱能力不可用**。Astra 更积极委派，因而更普遍支付了创建、失败、等待和整合成本。父任务仍有 13 道文档自动满分，故不能把每个低分都归给委派，也不能据此说多 Agent 一定没用。

应先做实际能力准入，返回可解释、无副作用的不可用结果；只在已有权限边界内选择可执行策略，无法满足隔离要求就不派发。**不能静默关闭沙箱、转宿主执行或扩大权限来提分。**DSH 的组合式子任务服务可作接口参考，但本轮未对其全部子任务生命周期做同等穷尽审查。

### 3.4 协议失败直接结束了尚未交付的工作

Qwen `wd2-swe-http-polling`：AReaL 最终原生状态为 `invalid_tool_call_index: negative … (event 276)`；最后仍在修自己的验证脚本，尚无最终回答。Codex 同题为 1，DSH 为 HARNESS_FAILED/0。Qwen `tb2-adaptive-rejection-sampler` 最终仅 5 条 Solve 账本，流中错误结束；桥记录 read timeout/502，不是功能测试证明算法错。

冻结 AReaL 对未接受的 HTTP 请求有 `max_retries=3`，但这不等于流中 completion 恢复；`generation.rs:1146–1173` 使用另一计数和配置，默认 completion 重试为 0。已存在“不执行不完整工具调用、丢弃未执行 completion”的正确边界，不能误写成完全没有恢复能力。

候选方向是区分：未派发调用的格式/流失败、已确认工具事实、未知副作用。前者可在有限实验中验证恢复；后两者不得重放。非法负 index 本身是供应商/协议违规，不应简单改成“接受任意 index”；Codex 的 Qwen 协议转换也使此配对不是纯 parser 单变量实验。

### 3.5 浏览器：点击成功与保存成功混淆，重复输出吞掉预算

Astra `wd-browser-triage`：AReaL 最终 0、DSH 1、Codex 0.6。本次回读 AReaL 最终原生包，验证并串接 3 个 SHA-256 冷历史分段后，得到 76 次 `run_command`；有多次相同 assignee/priority 选择，8 次 `P2` 同一 locator 点击，未见填入 `Filter Assignee`。有 3 次 compaction；最终 HTTP 400，对照桥日志是预算拒绝。原用户要求仍保存在 checkpoint，不能把它简化成“摘要把任务全忘了”。

DSH 轨迹明确采用“打开选择框 → 填过滤框 → 选择 → 关闭 → 重新加载核验”并提交结果；Codex 也尝试重载，但 priority、assignee 两项仍未通过。三方都会遇到 UI 状态语义；DSH 此次更快找到了能持久保存的动作链。

机制假设：全页快照与成功操作回执不能充分引导模型识别目标字段是否改变，重复相似动作缺少状态差分。候选应基于公开 UI 状态、更新前后目标字段及保存后重载，而不是按业务字段硬编码流程、固定失败次数后自动再点一次。该题使用公开 `browser.py`，不能把 GUI 内置 Browser 的全部设计直接算成被测能力。

### 3.6 数据/系统任务：满足公开样例，不等于满足输入类别

Astra 下两个 Codex 胜出、AReaL/DSH 均为 0 的配对：

- `tbpc030001-drive-persistent-pty-session`：AReaL 通过编译与手工交互后收尾；实际失败是 close 后仍有逃离进程组的后代。Codex 最终轨迹第 7、14 行的命令包含 `/proc` 后代枚举、逐后代清理，而非只有 `killpg`。
- `tbpc030001-recover-rotated-sqlite-wal-chain`：AReaL 验证了公开数据库可加载，最终逻辑仍按捕获编号排序帧；变体失败出现 WAL frame checksum 错。Codex 轨迹第 18、20 行已经按 checksum 链及提交边界搜索帧顺序，最终自动通过。DSH 的失败表现则为 committed WAL 不完整。

可迁移差异是**把需求转换为不变量、主动构造能推翻当前方案的输入**，而不是更多“编译成功”“样例能运行”。这两例不足以证明 Codex 的所有提升都源于提示；也不能把隐藏变体反馈写进产品策略。反向对照：Qwen `wd2-swe-sse` 是 AReaL/DSH 1、Codex 0，AReaL 轨迹做了分块/usage 帧等定向测试。

## 4. 代码层：三者的核心循环差在哪里

三者基本形态相同，都是模型驱动的“组装上下文 → 模型响应 → 工具 → 更新历史 → 再请求”。**分层更多、Rust 或插件更多，本身都不能解释分差。**

| 机制 | 冻结 AReaL | 冻结 DSH 发布实现 | Codex 同版本源码参照 | 对本轮的解释力 |
|---|---|---|---|---|
| 结束判定 | 无工具调用后检查待观察验证、子任务/交付，转 FinalAnswer；`generation.rs:680–823` | 无工具调用即 completed，但 `agent/turn-stopping` 可补入上下文；`dsh-agent-loop/lib/index.js:951–1012,1154–1157` | 合并 model follow-up 与 pending input，之后运行 stop hooks；`session/turn.rs:578–604,713–770` | 三者都不是通用答案验收器。AReaL 的生命周期闭环不能覆盖缺失业务约束 |
| 工具执行与调度 | 同一响应内 `for call in calls` 顺序执行；释放模型 permit 后才执行工具；`generation.rs:701–707,830–857` | parallel-safe 组并行、独占调用屏障、按模型顺序提交；`index.js:506–640` | `ToolCallRuntime` 与路由按能力装配 | 可减少无谓串行等待，尚无本轮耗时消融证明；不能盲目并行写操作 |
| 工具与模型适配 | 本次 Qwen 文档首请求列出 32 个工具，含历史、服务、委派等管理接口 | 同题常见 24 个工具，插件贡献 schema/context；headless 显式注入 cwd | `tools/spec_plan.rs:125–170` 按 ModelInfo、环境与策略建路由；本次 Qwen 文档首请求列 12 个工具，实际多用 exec_command | AReaL 认知面较大值得实验，但工具少不等于更强，使用一个工具也不等于只提供一个工具 |

### 工具协议的次级风险，不应冒充已证实主因

- `fs_read` 是字节 API；中文文件 `offset=1` 可切进 UTF-8 字符导致返回 base64。`wd2-doc-api-playbook` 有实际例子，但 Qwen 该题仍为 1。应改善文本读取边界，不能据此归因全部文档失败。
- 8192 字节回取页、`nextLine/nextCursor`、fileVersion 与私有 scratch 都增加使用成本。014 有错把 hash 当 cursor 的事件；原文可回取不保证模型实际取到了关键段落。
- `tools/results.rs:57–170` 的 observe 模式仍可做无损文件行转换。分析器必须读取持久 `contentItems`，不能直接把原始结果当模型所见；本次文档 normalizer 正是读取 contentItems。选查 `012/sources.json` 的 UTF-8 内容为 2,113 字节，与 displayedBytes 一致；不能把 rawBytes=3,058 误判成有损丢证据。

## 5. 哪些解释被反例削弱

1. **“AReaL 只要少崩溃就追上了”不成立。**Astra 的 AReaL 仅 2 个失败，Codex 有 5 个；AReaL 仍低 5.889 个百分点，正常低分与验收缺陷更重要。
2. **“全是长上下文/摘要问题”不成立。**文档无压缩；Qwen 文档首请求 token 中位数 AReaL 9,112、DSH 6,086.5、Codex 8,993.5，但 Astra 单次尝试文档中 Codex 首提示中位数约 11,025，比 AReaL 6,404 更大仍更好。长提示是实验变量，不是单一根因。
3. **“多做几轮就行”不成立。**Qwen 文档请求中位数 AReaL 17、DSH 20.5、Codex 13，两个对照都更好但方向相反；根预算耗尽后继续求解还可能失去交付机会。
4. **“更多 Agent 会补齐验证”被直接反证。**本轮文档 26 个 AReaL 子任务全因沙箱失败，没有提供预期独立检查。先证明可执行，再衡量收益。
5. **“应该照搬 Codex/DSH”不成立。**Qwen 下 AReaL 浏览器领先二者，DSH 的基础设施失败数还更多；当前组合的局部成功不能证明另一套整体架构更优。

## 6. 改进方案：最小共享机制与验证门禁

以下是设计候选，不是已实现或已证明提分的能力。保持 Clients → Core → Runtime；Core 不读隐藏评分材料、不内置本报告的题号或业务答案。

|---|---|---|---|
| P0 | **执行能力准入**：统一委派入口在模型工作前验证策略所需的沙箱/文件/网络能力，能力声明与实测一致；不可用立即说明 | 不静默降级隔离或转宿主；交互环境与外层容器分别验证 | 无模型的父 full-access/子受限、嵌套 namespace 不可用、取消和 UNKNOWN 回归；不可执行子任务数应降为 0 |
| P0 | **交付身份闭环**：有效 cwd、workspace、scratch 明确区分；检查实际交付集合、验证路径与文件版本 | 不禁止用户明确授权的外部路径；不自动搬运任意私有文件 | 不同真实根/符号路径、错误目录、生成后修改、异步验证、无关文件保护；核对最终文件而非自报路径 |

推荐的执行状态机不是再加一个隐藏“总指挥”：保留模型决策，但让 `观察 → 行动 → 证据 → 未完成要求 → 可交付/受阻` 的事实可见、可持久化；把协议终态与交付验收状态明确分开。可选完成检查也只能验证用户公开要求，不能偷读 Reward、把某种标题/格式当通用答案。
