# 桌面定时安排与每次执行分离

状态：proposed。以下记录已确定的产品方向，完整契约仍在设计中，不表示功能已经实现。

## 产品方向

GUI 的定时入口只表达“什么时候发起什么工作”，不提供前台／后台模式选择。安排支持一次性和重复；执行使用普通桌面任务的交互能力，依赖桌面 Host。需要批准的操作应展示受阻原因并等待用户批准，批准不扩大部署权限。

每次执行新建会话，不自动继承上一轮模型历史；各次结果关联回同一安排。工作目录与文件状态不因此隔离。Host 不可用时不启动桌面执行；恢复后将错过的触发合并为一次补执行。上一轮尚未结束时跳过本次触发，不排队、不重叠执行。

项目归属复用现有能力：用户可选择已有项目，或使用 GUI 已有的独立工作目录准备路径。不为取消项目依赖而引入新的 Core Workspace 领域对象。

## 交互、恢复与控制

审批等待超时后保留受阻执行并释放当前执行资源，不把过期审批变成长期授权。用户稍后选择继续时重新检查当前操作并申请批准。受阻执行仍属于未结束执行，因此后续触发跳过。

已经开始的执行因 Host 退出或服务重启中断时，保存原会话与执行记录，并要求用户明确恢复，不自动从头重跑。这与未开始安排在 Host 恢复后的补执行是不同路径；副作用结果未知时不得自动重放。

暂停安排只停止后续触发，不停止本次执行；停止本次执行只停止当前工作，不取消重复安排。编辑任务内容或时间只影响之后的执行。每次开始时读取项目或独立工作环境的当前模型与配置，冻结到本次执行；中途配置变化不改变已开始执行。

## 取舍

复用会话可以直接延续历史，但会把旧结论和指示带入后续检查。选择每次新建会话，使周期执行的模型上下文边界清楚；若需要跨轮资料，应明确提供，执行记录仍可统一查看。

补执行一次保留错过任务的机会，同时避免恢复后积压大量执行。跳过忙碌期间的触发避免同一安排重复审批和并发操作，但不能保证每个计划时间点都产生结果。

## 当前能力与设计约束

Core 当前 scheduled Task 绑定固定根 Thread，拒绝 interactive 交互及客户端动态工具；普通桌面审批默认等待 300 秒。新会话、Host 可用性与可恢复审批需要明确扩展，不能把现有 asynchronous 提问频道当作工具授权。

当前 Task/Run 权威状态由 Core 持有，桌面 Host 提供客户端能力。实现方案应优先复用这些所有者，不在 Renderer 建立独立定时器或第二份执行账本。调度与 Host 就绪握手的具体契约尚未确定。

## 未决边界

- GUI 创建与编辑流程、首期时间规则及其时区语义。
- 安排详情、执行会话和需要用户处理事项的展示。
- 现有安排与执行记录的兼容迁移方式。
- Core 调度、桌面 Host 就绪与新会话受理的具体契约；审批重新准备及未知副作用的恢复边界。

当前事实见 [Task 契约](../api/tasks.md)、[普通桌面审批](../../core/engine/src/desktop/interactions.rs) 和 [客户端工具 Host](../../core/app-server/src/dynamic_tools.rs)。
